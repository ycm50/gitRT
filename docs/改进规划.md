# GitRT 仓库改进评审与实施规划

> 评审方式：先由 **GLM-5.3-Flash** 出规划（`https://tierflow.cn/v1`，`reasoning_effort=none`），
> 再由主模型在本机（Windows + MSYS2 UCRT64）**逐条实地核实**：真编译、真跑 CTest、真跑功能套件、真查官方文档。
> 凡本文标注「已验证」的结论，都有可复现的命令与输出；标注「待核实」的，明确写出来，不当作结论用。

---

## 0. 结论摘要

**这个仓库不需要大修。** C++ 侧的实际质量明显高于同规模个人项目：手写 JSON 解析器有边界处理、
`QuoteArg` 的引号/反斜杠转义是对的、git 全程走 `CreateProcessW` + argv 数组**不经 shell**、
参数有分支名/远端名/修订/URL 白名单校验、`GIT_TERMINAL_PROMPT=0` + `CREATE_SUSPENDED` + Job 对象
（进程树一起收、超时/取消有独立退出码 124/130）、URL 里的凭据在显示时已脱敏、
`.gitignore` 已覆盖 `GitRT.ai.json`/`*.pem`/`.env`。

**缺的是「工程成熟度」，不是「功能正确性」。** 按投入产出比排序，最值得做的 5 件事：

| # | 事项 | 收益 | 成本 |
| --- | --- | --- | --- |
| 1 | 把 129 条已有断言从窗口程序里抽出来，做成**可独立运行的单元测试目标** | 高（测试从"要开桌面会话"变成"任意环境秒跑"） | M |
| 2 | CI 打开 `-DGRT_WERROR=ON` 并修掉 2 个真实告警 | 高（防止告警腐烂，一次就见效） | S |
| 3 | 版本号收敛到唯一真相源（`packaging/identity.json`） | 中高（现在三处硬编码，已不一致） | S |
| 4 | 加 `.gitattributes`，把行尾从"每台机器的本地配置"变成"仓库规则" | 中（消除跨机混合行尾/噪声 diff） | S |
| 5 | CI 去重：60 行工具链定位抽 composite action、功能套件不再跑两遍，**package job 直接复用 build 产物、不再重装 MSYS2 从零重建**（已核实可行） | 中高（维护成本 + CI 时长减半） | S–M |

## 2. 已核实的问题清单

### 2.1 `GRT_WERROR` 形同虚设，且已有 2 条真实告警 —— 已验证

`GRT_WERROR` 选项在 [CMakeLists.txt:37](../CMakeLists.txt#L37) 定义了，但 CI 从不启用；默认 `OFF`。
本机实测 `-DGRT_WERROR=ON` 后编译中断于 2 处：

| 位置 | 告警 | 性质 |
| --- | --- | --- |
| [src/core/command_builder.cpp:366](../src/core/command_builder.cpp#L366) | `-Wmisleading-indentation` | **真实可读性隐患**：`if (!ValidateFlagValues(...)) return false;` 和下一条 `const std::vector<std::wstring> flagsArgv = ...;` 挤在同一行，早期返回与后续初始化视觉上粘在一起 |
| [src/core/remote.cpp:53](../src/core/remote.cpp#L53) | `-Wunused-function` | 死代码：`ShortHash()` 定义后从未被调用 |

**建议**：拆开 366 行；`ShortHash` 二选一——删掉，或让另外两处内联重复实现改用它
（[src/core/remote.cpp:96](../src/core/remote.cpp#L96) 与 [src/core/restore.cpp:127](../src/core/restore.cpp#L127)
都在手写同一个 `rev-parse --short`，共 3 处重复）；然后在 CI 构建步骤加 `-DGRT_WERROR=ON`。

**验收**：CI 中出现 `-DGRT_WERROR=ON` 且构建通过；`cmake --build` 输出 `0 warning`。

### 2.2 版本号有 3 个写入点，且已经不一致 —— 已验证

`packaging/identity.json` + [cmake/identity.cmake:26](../cmake/identity.cmake#L26) 明确自称
"身份与打包参数的**唯一真相源**"（导出 `GRT_ID_VERSION`，当前 `0.1.0.0`）；但
[CMakeLists.txt:2](../CMakeLists.txt#L2) 写 `project(GitRT VERSION 0.1.0)`、
[CMakeLists.txt:30](../CMakeLists.txt#L30) 写 `GRT_VERSION="0.1.0"` —— **三处各写一份，已经不一致**（0.1.0 vs 0.1.0.0）。

而 `GRT_VERSION` 是**用户可见**的：进 WinHTTP User-Agent（[src/core/ai_client.cpp:194](../src/core/ai_client.cpp#L194)）
与「关于」对话框（[src/gui/internal_commands.cpp:122](../src/gui/internal_commands.cpp#L122)）。

**建议**：`GRT_VERSION` 由 `GRT_ID_VERSION` 派生，并在配置期加一条 `FATAL_ERROR` 断言二者一致。
**补充核实（比"三处都改"更彻底的做法）**：全仓库搜索 `PROJECT_VERSION` / `CMAKE_PROJECT_VERSION` —— **没有任何地方使用**。
所以 `project(GitRT VERSION 0.1.0 ...)` 里的版本号是纯冗余信息，直接去掉 VERSION 即可
（`include(cmake/identity.cmake)` 在第 19 行，早于第 30 行的 `add_compile_definitions`，
`GRT_ID_VERSION` 那时已经在目录作用域里可用）：
`project(GitRT LANGUAGES CXX RC)` + `GRT_VERSION="${GRT_ID_VERSION}"`。
这比"在 `project()` 之前再 `file(READ)` + 正则解析一遍 identity.json"更好——不要写第二个解析器。
> 注意：`cmake/identity.cmake` 会 `configure_file` 到 `CMAKE_BINARY_DIR`，所以**不能**把它整体挪到 `project()` 之前。

**验收**：只改 `identity.json` 的 version，`GitRT.exe` 的 User-Agent / 关于对话框 / 清单三者同步变化；
手改 `CMakeLists.txt` 制造不一致时配置期直接失败。

### 2.3 没有 `.gitattributes`，行尾完全依赖每台机器的本地配置 —— 已验证

`git ls-files --eol` 实测：**130 个文件索引内是 `lf`、工作区是 `crlf`**，本机 `core.autocrlf=true`，
仓库**没有任何 `.gitattributes`**。也就是说"现在一致"是本地配置的巧合，不是仓库规则：

- `autocrlf=false` / `input` 的贡献者得到 LF 工作区 → 谁碰过文件谁就产生整文件行尾翻转的噪声 diff；
- 更实际的风险是 `.rc`（用 `--codepage=65001` 编译）和 PowerShell 脚本：`setup-msys2` 的**官方文档专门有一节
  "Known Problems: actions/checkout and line endings"**，原话是"若不配置 git attributes，git 可能把文本文件自动转成
  Windows 行尾，从而导致 MSYS2 工具出问题"，并建议 `git config --global core.autocrlf input`。

**建议**：加 `.gitattributes`：`* text=auto eol=lf`、`*.ps1 text eol=crlf`、`*.ico/*.png binary`、
`*.rc text eol=lf`；顺手加 `.editorconfig`。注意：这是一次**会改写全库行尾的提交**，要单独一个 commit、单独 review。

**验收**：`git ls-files --eol` 中 `i/lf w/lf`（或与规则一致）占绝对多数；新克隆的机器上构建与自检全绿。

### 2.4 129 条断言被锁在窗口程序里，没有可独立运行的单元测试 —— 已验证（本报告最高价值项）

项目**没有单元测试框架**（受"零第三方依赖"约束，不该引入 Catch2/gtest）。但"没有测试"是错觉：

- [src/gui/main.cpp](../src/gui/main.cpp)：`check()` 断言 **81 条**；
- [src/shellprobe/main.cpp](../src/shellprobe/main.cpp)：**48 条**；
- 合计 **129 条**，覆盖了大量**纯函数**：`IsValidUrl` / `IsValidBranchName`（[main.cpp:202](../src/gui/main.cpp#L202)）、
  `AiModelsUrlFromEndpoint` 的 4 种端点形态（[main.cpp:387-392](../src/gui/main.cpp#L387-L392)）、
  AI 配置往返与 Key 优先级（[main.cpp:343-423](../src/gui/main.cpp#L343-L423)）、porcelain 解析、tag/squash 计划构造……

问题在于它们**只能在 `GitRT.exe` 里跑**：`RunSelfTest(HWND mainWnd, ...)`（[main.cpp:58](../src/gui/main.cpp#L58)）
接收窗口句柄，[main.cpp:238](../src/gui/main.cpp#L238) 还真的 `CreateParamPanel(mainWnd, ...)` 建了一个窗口，
入口 main 里先 `InitCommonControlsEx` + `CoInitializeEx` + `CreateWindowExW`（[main.cpp:911-934](../src/gui/main.cpp#L911-L934)）。

**后果**：想验证 `QuoteArg` 或 URL 校验，必须启动一个 GUI 程序、等 2 秒、读一份写出来的 txt；
非交互会话/容器里根本跑不了；失败定位只能看日志。

**建议**：新增 `src/tests/`（或 `tests/`）+ CMake 目标 `gitrt_selftest_core`，**不链接任何 GUI 代码**，
只链接 `gitrt_core`：把纯函数断言搬过去（`check()` 那套 lambda 直接复用，或抽成一个 30 行的
`tests/check.h`），注册成 CTest 用例。窗口相关的断言留在 `--self-test` 里。
纯函数都现成——`QuoteArg`、`IsValid*`、`JsonEscape/JsonUnescape/StripCodeFence`、
`AiModelsUrlFromEndpoint`、`ParsePlanReply`、`next-version.ps1` 的进位规则（这个要 PowerShell 侧测）。

**验收**：`ctest` 里多出至少 1 个**纯控制台**用例，`0 窗口 0 秒级`完成，断言数 ≥ 现有纯函数断言数；
`build/<cfg>/src/tests/GitRT.SelfTestCore.exe` 能在无桌面会话下直接跑。

### 2.5 CI：60 行工具链定位脚本逐字重复两遍 + 功能套件跑两遍 —— 已验证

- `.github/workflows/build.yml` 的 build job（[:73-112](../.github/workflows/build.yml#L73-L112)）与
  package job（[:275-312](../.github/workflows/build.yml#L275-L312)）里的「定位 UCRT64 工具链」**逐字相同**，
  工作流注释自己都写着"两个 job 的这一步内容必须保持一致（改一处要同步另一处）"。
- 功能套件（[:216-236](../.github/workflows/build.yml#L216-L236)）在 `matrix: [Debug, Release]` 里各跑一遍 ——
  同一批纯 CLI 端到端用例跑两次。
- **更正一个我原本的判断**：`setup-msys2` 的 `cache` 输入**默认就是 `true`**（官方 README 明确），
  所以"CI 没有缓存"是**错的**，不该写进改进项。真正可考虑的是 `release: false`
  （复用 runner 镜像自带的 MSYS2 而不是每次全新安装）——**此项待核实**：需确认镜像里是否已装齐
  `mingw-w64-ucrt-x86_64-{gcc,binutils,cmake,ninja}`。

**建议**：抽成 `.github/actions/find-ucrt64/action.yml`（composite action），两个 job 都 `uses:` 它；
功能套件用 `if: matrix.config == 'Release'` 只跑一次，Debug 只跑 CTest + 自检。

**再加一条更大的（已核实可行）**：package job 现在**重装一遍 MSYS2 并从零重建 Release**，
而 build 矩阵里的 Release 那一路已经做了同样的事，并且已经把产物上传成 `gitrt-binaries-Release`
（含 `GitRT.exe` / `GitRT.Shell.dll` / `GitRT.ShellProbe.exe` / `packaging/AppxManifest.xml`）。
核实结论：
- `packaging/scripts/build-msix.ps1 -LayoutOnly` **只需要** CMake 生成好的 `AppxManifest.xml` + 源码里的
  `packaging/Assets/*`，**不需要编译器、不需要 Windows SDK**（makeappx/signtool 只在非 LayoutOnly 分支用）；
- `packaging/scripts/build-release.ps1` 是用 **递归查找** 定位二进制的（第 35-42 行），对目录层级不敏感。
所以 package job 可以 `needs: build` + `download-artifact` 后只做"组装 + 安装/卸载端到端"，省掉整段工具链安装与重建。
**唯一的改造点**：`download-artifact` 会把文件平铺到同一目录，而 `build-msix.ps1` 期望
`<OutDir>\<Config>\packaging\AppxManifest.xml` 这个层级 —— 要么下载到对应子目录，要么给脚本加一个
`-ManifestPath` 参数。

**验收**：`workflow.yml` 里不再出现重复的候选路径列表；package job 不再安装 MSYS2、CI 总时长明显下降，
且发布包内容与改造前逐字节可比（`Get-FileHash` 比 zip）。

### 2.6 AI 客户端硬要求 API Key，本地无鉴权端点不可用 —— 已验证

[src/core/ai_client.cpp:326](../src/core/ai_client.cpp#L326)（拉模型列表）与
[:495](../src/core/ai_client.cpp#L495)（生成计划）在 `ResolveApiKey()` 为空时**直接报错返回**。
于是任何**不需要鉴权的本地 OpenAI 兼容服务**（Ollama / LM Studio / vLLM / llama.cpp server）都用不了——
用户必须随手编一个假 Key 才能用。这与 README 主打的"接口地址可配"是矛盾的。

**建议**：key 为空时，若 endpoint 主机是 `localhost`/`127.0.0.1`/`::1` 就照常发请求（不带 `Authorization` 头）；
或在设置里加一个显式的「不需要鉴权」复选框。两种都能一次讲清。

**实测证据（A/B 对照，本机跑的）**：把 endpoint 指向仓库自带的 `tools/mock-ai-server.ps1`，只切换 Key 有无：

| 场景 | `key_set` | `http` | `elapsed_ms` | 结果 | mock 服务端日志 |
| --- | --- | --- | --- | --- | --- |
| 不设 Key | 0 | **0** | 0 | `error=未配置 API Key…` | **没有收到任何请求** |
| 设了 Key | 1 | 200 | 16 | `ok=1 command=sync.push` | 收到 `POST /v1/chat/completions` |

即：不是"发出去被 401 拒绝"，而是**客户端在本地就拦下了，压根没连**。

**验收**：指向本机 Ollama（`http://127.0.0.1:11434/v1`）不填 Key 也能拉到模型列表并生成计划。

### 2.7 `tools/*.ps1` 重复度很高 —— 已验证（量化）

对 21 个脚本做逐行去重统计：**73 行不同代码在 ≥4 个脚本里重复出现**，典型是：

| 重复次数 | 代码 |
| --- | --- |
| 12× | `function Check($what, $ok, $detail = '') {` |
| 12× | `$pass = 0; $fail = 0` |
| 9× | `if ($ok) { $script:pass++; Write-Host "  [PASS] ..." }` / `else { ... [FAIL] ... }` |
| 9× | `Write-Host "== 结果: $pass 通过 / $fail 失败 =="` |
| 19× | `Get-Process GitRT -EA SilentlyContinue \| Stop-Process -Force` |
| 8–10× | `[DllImport("user32.dll")] ... GetWindowRect / GetDlgItem / SendMessageW` |

**建议**：抽 `tools/lib/harness.ps1`（`Check`/结果行/退出码）与 `tools/lib/win32.ps1`（P/Invoke 声明），

**验收**：`tools/` 下不再有第二份 `function Check`；各脚本仍报同一条 `== 结果: N 通过 / 0 失败 ==`。

### 2.8 明文 HTTP 端点没有任何告警 —— 已验证

[src/core/ai_client.cpp:190](../src/core/ai_client.cpp#L190) 只在 `nScheme == HTTPS` 时加 `WINHTTP_FLAG_SECURE`，
而 URL 校验（[src/core/command_builder.cpp:59](../src/core/command_builder.cpp#L59)）是**允许 `http://`** 的。
一旦用户把接口地址填成非本机的 `http://`，**API Key 与提示词（含仓库路径、分支名、文件名）就是明文过网**。
注意这里的分寸：Key 明文落盘是**写在注释里、用户明确选择**的产品决策
（[src/gui/settings_window.cpp:8](../src/gui/settings_window.cpp#L8)），不该被当成 bug 指责；
缺的是**"http + 非本机"时的显式告知**。

**建议**：（a）非本机 `http://` 时在设置界面/生成前给一条明确警告；（b）可选提供 DPAPI（`CryptProtectData`，零依赖）
加密落盘，默认仍保持明文，让用户选。**不要**擅自改成强制加密——那会破坏"随时可查看与修改"的产品决策。

**验收**：填 `http://192.168.x.x/v1` 时界面出现可见警告；填 `https://` 时不出现。

## 3. 已排除的疑点（明确不要改）

这些我都查过，**没有问题**，写在这里是为了防止后来者重复怀疑、甚至"改坏"：

1. **`WinHttpCrackUrl` 会不会丢查询串？不会。** 代码没有设置 `lpszExtraInfo`
   （[src/core/ai_client.cpp:179-186](../src/core/ai_client.cpp#L179-L186)），

## 6. 本次评审的局限（诚实说明）

1. **本地是 depth=1 浅克隆**（`.git/shallow` 存在，`rev-list --count HEAD` = 1，且无本地 tag）。

3. **没做性能压测**：状态面板/预览刷新的实际开销我只做了代码路径分析，没有测大仓库（如 10 万提交）下的表现。

   理论上适合 fuzz，本次只做了阅读级审查，没有构造恶意输入。
5. **方法学备注**：GLM-5.3-Flash 在本接口上 `reasoning_content` **与正文共享 `max_tokens` 预算** ——
   首次调用 12000 token 全被思考吃光、正文为空（`finish_reason=length`）。

## 15. 用户需求：「标签列表」「发布列表」实现（2026-09-26）

### 15.1 GLM 的 4 条决策与本轮取舍

| 问题 | GLM 结论 | 是否照做 |
| --- | --- | --- |
| 形态 | 复用已有窗口，不新建只读窗（"同一数据两个入口，加列必漂移"） | ✅ 照做 |

**为什么偏离"专用退出码"**：`exit=1` 是 `tools/test-all.ps1:148` **明确断言的契约**

### 15.2 根因与修法

数据层（`LoadTags` / `LoadReleases`）与两个窗口（`LVS_REPORT` 列表、选中即填表单、创建/推送/删除表单）
**早就存在**；缺的只是 `ExecuteInternalCommand()` 里没有 2307/2311 的 `case` → 落到 `default:` 弹
「该功能尚未实现（当前为 GUI 首个增量）」。**真正的问题是"内部命令的去向"散在一个 switch 里，
没人能回答"每个命令都有去处吗"**，于是：
- 抽出唯一一份纯函数映射 `ActionOfInternal()`（15 个内部命令）+ `OpensDedicatedWindow()`；
- 参数面板的 `UsesDedicatedWindow()` 不再另抄一份名单（原来只有 4 个写命令 —— 正是漏掉这两个的原因）；

## 16. CI 的「文档体检」job 为什么失败（并按用户要求去掉它）

现象：GitHub Actions 里 `文档体检（站内链接 / 表格列数）` **failed in 10s**，而本机一直通过
（本地 10 个 `.md` 全过）。用户要求去掉这个检查。

### 16.1 定位：先证伪最像的假设，再精确复现

| 假设 | 验证方式 | 结论 |
| --- | --- | --- |
| 行尾差异（CI 检出是 LF，本机工作区是 CRLF） | `git clone` 出一份 LF 检出（`git ls-files --eol` 全 `i/lf`），在里面跑同一条命令 | ❌ **通过**（exit=0）—— 不是行尾问题 |
| **stdout 代码页**：脚本打印中文，而 runner 的 stdout 是西文代码页 | `PYTHONIOENCODING=cp1252 python tools/check-docs.py` | ✅ **精确复现**：`UnicodeEncodeError` 回溯 + 退出码非 0（本机是 GBK，中文能编出去，所以照过） |

### 16.2 处置

- **去掉 CI 里的 `docs` job**（用户要求）：workflow 里的 job 与头部注释、README 的 CI 表格行、
  CONTRIBUTING 的"提交前第五件事"都相应改回/删除（列表回到"四件事"）。
- **工具保留**在 `tools/check-docs.py`，作为**本机可选**检查（CONTRIBUTING 写明用法与 `-X utf8`）。
- 想恢复成 CI 门禁只需两步：把 job 加回去 + 命令带 `-X utf8`（已验证 `python -X utf8 tools/check-docs.py`
  在 cp1252 下也通过）。

> **教训**：Python 脚本往 stdout 打非 ASCII 字符，**跨环境就会炸** —— 本机的中文代码页会把问题
> 掩盖到 CI 才暴露。要么 `-X utf8`（或 `PYTHONUTF8=1`），要么只往 stdout 写 ASCII、把中文文案
> 放进文件或环境变量兜底。

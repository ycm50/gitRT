# 数据与状态模型（config.json / 日志 / 快照 / 状态解析）

> 这一页讲"状态存在哪、谁能写、什么时候失效"。改这些地方很容易引出"界面不刷新"
> 或"配置互相覆盖"这类难查的 bug，所以把契约写清楚。

## 1. `config.json`：扁平键值表，不是结构化配置

位置 `%APPDATA%\GitRT\config.json`，由 `src/core/config.cpp` 的 `ConfigStore` 统一读写。设计要点：

- **扁平键值**（键可含点号：`flags.sync.push.tags`），因为它是**多进程共享**的（Shell DLL 切开关、
  GUI 存 AI 配置）。整文件覆盖写会丢掉别人刚写的键 —— 所以读写都经过同一个有序表。
- **未识别的键原样保留**；损坏的 JSON 备份成 `config.bad-<ts>.json` 后以默认值继续。
- **读到的是带 5 秒节流的缓存**（`Reload()` 默认节流、`force` 可绕过）：Explorer UI 线程里不能频繁读盘。
- 写盘是**原子替换**（同目录 `.tmp` → `MoveFileEx(REPLACE_EXISTING)`）。

常用键：

| 键 | 类型 | 谁写 | 说明 |
| --- | --- | --- | --- |
| `flags.<cmdKey>.<flagKey>` | bool | Shell 菜单（tree 形态切开关）/ 各处 | 复选状态持久化，**flagKey 必在白名单** |
| `menu.mode` | string | 用户手改 | `app`（默认）/ `tree` |
| `menu.directTop` / `menu.hiddenGroups` / `menu.hiddenCommands` | string[] | 用户手改 | 只影响 tree 形态 |
| `menu.showFlags` | bool | 用户手改 | tree 形态里是否把开关铺进菜单 |
| `autoFetchMinutes` | int | 首选项 | 0 = 关；主窗口每 60 s 看一次 |
| `aiEndpoint` / `aiModel` / `aiApiKeyEnv` / `aiTimeoutMs` | - | 首选项（AI 设置） | `GitRT.ai.json` 的**备份副本**，供没装 GUI 的路径读 |

`GitRT.ai.json`（exe 同目录）才是 AI 配置的**主存储**；`config.json` 里那几项是兼容与兜底。

## 2. `git status` 的解析：只用 porcelain v2 -z

`src/core/status.cpp` 的 `ParsePorcelainV2()` 只认 `--porcelain=v2 -z --branch --show-stash`：

- **NUL 分隔**（`-z`）：路径里可以有空格/中文/引号，按行切会碎；
- 重命名条目（`2 R.`）**多一个 NUL token**（原路径在新路径之后），少读一个就会把下一行当成路径；
- 头部是 `# branch.oid` / `# branch.head` / `# branch.ab +N -M` / `# stash N`；
- 缺 `branch.ab` 是正常的（没有上游时就不给），**不能当解析失败**。

状态查询另外注入 `--no-optional-locks`（等价 `GIT_OPTIONAL_LOCKS=0`）：只读查询不该写 index。

## 3. 快照与 Broker：现在是"乐观显示"

`src/shell/snapshot_reader.*` 是"只读、无锁 seqlock"的读者；`src/shell/broker_client.*` 能往
`\\.\pipe\GitRT.<sid>.v1` 写一行 JSON。**但 Broker 还没接**：今天的实际路径是"检测不到 Broker →
直启 GUI"，菜单里的状态一律按"未知/乐观"显示（不隐藏命令，真正的闸门在参数面板）。

为什么菜单构建期**一次 git 都不调**：`GetTitle/GetFlags/GetState/EnumSubCommands` 跑在 Explorer 的
UI 线程里，预算是 10 ms；实测 app 形态 0.001 ms、tree 形态 0.02 ms。任何一次 git 调用都会让右键卡顿。
仓库探测只做**文件系统**判断（`ProbeRepo`：看 `.git` 是目录还是文件、合并/变基标记文件在不在），
不启动进程。

## 4. 请求段（共享内存）的契约

Shell DLL → GUI 的上下文交接走命名共享内存段（`src/core/request_section.*`）：

```
Local\GitRT.Req.<pid>-<tick>-<seq>
[GrtReqHeader][paths: len+NUL...][optionsJson]
```

- 头部含 `magic=0x51525247` / `version=1` / `headerSize` / `cmdId` / `selMask` / `pathCount` /
  `pathBytes` / `optionsBytes`：接收方先映射头部拿长度，再整体映射（不把段大小写死）；
- **写完不能立刻 CloseHandle**：段在最后一个句柄关闭时销毁，接收方还在 CreateProcess 路上会拿到
  `ERROR_FILE_NOT_FOUND`。FIFO 保活最多 8 个句柄（有界）；
- `optionsJson` 里带 `cmdKey` 与 `repoRoot`，GUI 侧**交叉校验 id 与 key**，不一致直接拒绝执行
  （DLL/GUI 版本脱节时宁可不开，也不要按错的命令执行）。

## 5. 谁来决定"刷新"

| 触发 | 动作 |
| --- | --- |
| 命令执行结束 | `WM_GRT_STATUS_RELOAD(wp=1)` → 重读 `git status` 再刷视图 |
| 切换/选择仓库 | `RefreshRepoStatus()` + 刷状态视图 + 底部栏 |
| 自动抓取完成 | `WM_GRT_STATUS_RELOAD(wp=1)` |
| 查看类命令的面板 | 2.5 s 定时器重算内容（`WM_GRT_PANEL_PREVIEW`） |
| 手工点「刷新」 | `RefreshRepoStatus()` |

`wp=0` 只刷视图、**不重读**：这是"执行完状态没变"的经典原因（04 §7）。

## 6. 状态模型里没有的东西（有意为之）

- 没有数据库、没有索引缓存、没有 watcher：每次要看状态就重读 `git status`（快、不会脏）；
- 不缓存 `git log` 结果：查看类命令每 2.5 s 重算一次；
- 不记录"最近操作"历史到磁盘（`recent.json` 只在设计文档里，尚未实现）。

## 1. 产品定位

### 1.1 一句话

> 把 Git 的高频操作放回你**已经在的地方**——资源管理器的右键菜单；用**分层菜单 + 复选开关 + 参数面板**，让图形界面具备命令行级表达力，而用户不必记住任何命令。

### 1.2 背景与问题

Windows 上"右键菜单里的 Git"长期只有两个选择，各有明显缺口：

- **TortoiseGit（事实标准，但已显老旧）**：它是传统 Shell 扩展路线，在 Windows 11 上**只能出现在「显示更多选项」里**，用户必须多点一次（或按住 Shift）；其状态缓存/日志窗口/差异窗口的交互与视觉停留在 Windows 7 时代。
- **独立 Git GUI（Fork / SourceTree / Git Extensions / GitHub Desktop）**：功能完整，但与文件系统脱节——用户已经在资源管理器里选中了文件，却必须切到另一个应用窗口，再手动把"上下文"搬过去。
- **命令行**：最精确，但每次都要先开终端、`cd` 到目录。

真正的痛点是**"对象"与"动作"的分离**：选择对象的地方（资源管理器）没有动作，有动作的地方（CLI/GUI）没有对象。

Windows 11 为此提供了官方的现代菜单扩展机制（`IExplorerCommand` + 应用标识），但它的注册流程**相对隐蔽**（需要 Sparse MSIX 打包、签名、以及在 DLL 内嵌 `msix` 身份清单，见 §3.4），导致绝大多数 Win32 程序至今仍停留在"显示更多选项"里。这既是本产品的技术门槛，也是差异化机会。

### 1.3 目标用户

| Persona | 画像 | 核心诉求 |
| --- | --- | --- |
| **P1 日常开发者（主力）** | 每天在 IDE 和资源管理器之间切换；会用 Git 但不想背参数；装了 TortoiseGit 但嫌它慢/丑 | 选中文件就能提交/推送/切分支；危险操作有清晰确认 |
| **P2 命令行熟练用户** | 习惯 `git` 原生命令，Neovim/Terminal 工作流；对 GUI 封装不信任 | 需要"菜单 → 一行等价命令"的可复制、可审计路径；能直传 `--flags` |
| **P3 半技术用户 / 设计同学** | 只会"拉取、提交、推送"三件事；怕弹窗、怕冲突 | 极简默认菜单、错误用中文人话解释、绝不静默搞坏工作区 |

### 1.4 价值主张（相对竞品的差异点）

1. **原生现代菜单，无需「显示更多选项」**——Win11 上的第一等公民。
2. **分层 + 复选 + 参数**：一级入口不堆命令；开关型选项（`--rebase`、`--include-untracked`、`--prune`）以复选状态直接反映在菜单上；带参命令弹"命令面板"预填参数。
3. **菜单构建期零 Git 调用**（§3.7）：右键响应速度作为产品特性，而不是"能用就行"。
4. **git CLI 是唯一真相源**（§5.4）：hooks、LFS、Git Credential Manager、`core.autocrlf`、safe.directory 全部按用户既有配置生效，行为可预期。
5. **MIT 开源、无遥测、可审计**：与 Git 生态的许可证兼容性已逐项核对（§5.8.4）。
6. **会说人话，但绝不乱动手**（v0.2 新增，§4.3 层级 4）：用自然语言描述意图即可得到一条**可审阅、可复制**的等价命令；AI 只负责"选哪条命令、填什么参数"，执行权始终在用户手上，且方案必须通过命令表白名单闸门——这是与"让 AI 直接跑 shell"的产品的本质区别。

### 1.5 非目标（Non-goals，明确不做）

- ❌ 不替代 `git` CLI 做完整工作流编排（不提供"一键发版"）。
- ❌ 不自研 Git 协议 / 对象库 / 差异算法（见 §5.4 的理由）。
- ❌ 不做 Git 服务端（GitHub/GitLab）账号体系、PR 评审、Issue 管理。
- ❌ 不做跨平台（Windows 11 专属）。
- ❌ 不做遥测、不做"云同步配置"。
- ❌ v1 **不做图标覆盖（overlay icons）**——技术上与 D1 冲突，见 §3.9。
- ❌ 不做传统菜单注册（D1）；但这会在 §3.8 产生一个必须向用户交代的可见性缺口。
- ❌ **不做通用 AI 助手**：不聊天、不生成代码、不解释 Git 原理、不执行命令表以外的任何操作（v1 单轮，见 Q12）。

## 3. 平台技术约束（本产品的"物理定律"）

> 本章是全文档最重要的部分。**这些约束由 Windows 决定，不由我们决定**；架构必须迁就它们。
> 凡标注 `⚠️待实测` 的结论，必须在 M0 阶段用真实机器验证后才可当作设计前提。

### 3.1 现代菜单的三件套（缺一不可）

一个命令要出现在 Win11 现代右键菜单里，必须同时具备：

1. **原生 COM DLL**，实现 `IExplorerCommand`（实现 `IEnumExplorerCommand` 以提供子菜单）。
2. **包清单中注册 COM 类**：`<com:Extension Category="windows.comServer">` → `com:SurrogateServer` → `com:Class Id="{CLSID}" Path="GitRT.Shell.dll" ThreadingModel="STA"`。
3. **包清单中注册命令与目标类型**：

```xml
<desktop4:Extension Category="windows.fileExplorerContextMenus">
  <desktop4:FileExplorerContextMenus>
    <desktop5:ItemType Type="Directory">
      <desktop5:Verb Id="GitRT" Clsid="{CLSID}" />
    </desktop5:ItemType>
  </desktop4:FileExplorerContextMenus>
</desktop4:Extension>
```

依据：[Microsoft Learn · Add a File Explorer context menu command to a packaged desktop app](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer)。

### 3.2 必须有"包标识"，因此必须有 Sparse MSIX

我们的程序是**传统 Win32 安装**（exe 放在 `C:\Program Files\GitRT`），不是 Store 应用。要拿到包标识，必须额外安装一个**空的 Sparse MSIX"身份包"**：

- 清单关键项：`uap10:AllowExternalContent=true`、`rescap:runFullTrust`、`rescap:unvirtualizedResources`、`Application` 用 `uap10:TrustLevel="mediumIL" uap10:RuntimeBehavior="win32App"`、`VisualElements AppListEntry="none"`、`ProcessorArchitecture="neutral"`。
- 安装：`Add-AppxPackage -Path GitRT.msix -ExternalLocation "C:\Program Files\GitRT"`。
- 卸载：`Get-AppxPackage GitRT | Remove-AppxPackage`（**必须在独立的 powershell 进程里执行**；在已加载该包的会话内执行易出现 `0x80073CFA` 半卸载残状态——社区经验）。
- **版本冲突是硬规则**：同一个 `Version` 重复注册会失败（`0x80073CF9`），升级前必须先卸载旧包。
- 身份包与"真正的文件"分离：**DLL 改了通常不需要重新注册包**（身份未变）；改了清单才需要升版本并重新打包。

依据：[Grant package identity by packaging with external location manually](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps)、[xplorer² 实践记录](https://www.zabkat.com/blog/win11-explorer-menu-package.htm)。

### 3.3 签名是硬性成本，必须提前决策

| 方案 | 成本 | 可用性 | 适用 |
| --- | --- | --- | --- |
| **自签名证书** | ¥0 | 任何地区 | **仅开发机**：需把公钥 `.cer` 导入 `Cert:\CurrentUser\TrustedPeople`，否则注册报 `0x800B0109 (CERT_E_UNTRUSTEDROOT)` |
| **SignPath Foundation（开源免费签名）** | ¥0 | 需申请、有资格审核 | **本项目（MIT 开源）的首选分发签名路径** |
| **Azure Artifact Signing**（原 Trusted Signing） | ≈$9.99/月 | 组织：美/加/欧盟/英；**个人：仅美国、加拿大** | 无法用于中国大陆的个人开发者 |
| **OV 证书**（DigiCert/Sectigo 等） | $150–300/年 | 全球 | 中国区开发者的现实选择；2023-06 起私钥必须存 HSM/U 盾 |
| **EV 证书** | $400+/年 | 全球 | **2024 年起不再有 SmartScreen 免警告优势，不建议为此时购买** |
| **Microsoft Store 上架 MSIX** | ¥0（商店代签） | 全球 | 可作为分发渠道之一，但需过审 |

**结论**：开发期自签名；对外分发优先申请 **SignPath Foundation**（开源免费），备选 OV 证书。这一项是**项目公开发布的前置条件**，建议 M0 期间就开始申请流程（审核有周期）。

依据：[Code signing options for Windows app developers](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)、[Certum Open Source Code Signing](https://shop.certum.eu/open-source-code-signing.html)。

### 3.4 ⚠️ 关键坑：DLL 必须内嵌 MSIX 身份清单

除了 MSIX 包清单，**DLL 自身的 side-by-side 清单里必须内嵌匹配的 `msix` 元素**，否则资源管理器**静默不加载**扩展（无报错，最难排查）：

```xml
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity version="0.0.0.0" name="GitRT"/>
  <msix xmlns="urn:schemas-microsoft-com:msix.v1"
        publisher="CN=..."           <!-- 必须与 MSIX Identity/@Publisher 完全一致 -->
        packageName="GitRT"          <!-- 必须与 MSIX Identity/@Name 一致 -->
        applicationId="GitRT" />     <!-- 必须与 MSIX Application/@Id 一致 -->
</assembly>
```

最小化踩坑成本的手段：**在 M0 就把 `publisher / packageName / applicationId` 三个值收敛为单一来源**（例如 `packaging/identity.json`），由 CMake 同时生成 `.rc` 里的清单和 `AppxManifest.xml`，杜绝手工不一致。

依据：[xplorer² 实践记录](https://www.zabkat.com/blog/win11-explorer-menu-package.htm)（作者为此损失 4–5 天）、[Microsoft Learn · 添加身份元数据](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps)。

### 3.5 ItemType 能力矩阵

| `desktop5:ItemType/@Type` | 含义 | 状态 |
| --- | --- | --- |
| `*` | 任意文件（多选文件时） | ✅ 官方支持 |
| `Directory` | 选中的文件夹 | ✅ 官方支持 |
| `Directory\Background` | 文件夹空白处 | ✅ 官方支持 |
| `Drive` | 驱动器根目录（`C:\`） | ⚠️待实测：`desktop10:ItemType Type="Drive"` 打包成功但社区报告**不出现任何菜单项** |

`⚠️待实测`：驱动器根目录、库（Library）、桌面、`此电脑` 等特殊 Shell 位置**能否出现我们的命令**，M0 逐一验证并写入《支持矩阵》，避免用户报"为什么我在 X 上没有菜单"。

### 3.6 菜单条目数量与级联

- **单个菜单处理器最多 16 项**（分隔符不计入）。这是 NanaZip 作者实测的限制，**微软官方文档未记载**。
- 绕过方式：注册**多个 Verb/CLSID**（每个处理器各 16 项）。
- Win11 会在某个应用有多个 verb 时**自动级联**成一个子菜单。
- ⚠️待实测：**嵌套层（`EnumSubCommands` 返回的子菜单）是否也受同一 16 项上限约束**。

依据：[@MouriNaruto · Share my experience of implementing context menu support for File Explorer in Windows 11](https://mouri.moe/en/2021/12/25/Share-my-experience-of-implementing-context-menu-support-for-File-Explorer-in-Windows-11/)。

**对本产品的含义**：D2 要求"完整功能清单 + 分层"，命令总数必然 > 16。因此：

1. 顶层**只注册 1 个 Verb**（`GitRT`），呈现为一个可展开的级联子菜单。
2. 所有具体命令通过 `IEnumExplorerCommand` 在子菜单里分层给出（§4.1）。
3. 若 M0 实测发现单层 16 项上限在子菜单同样生效，则按"分组 → 二级子菜单"分摊（必要时用多 CLSID 方案）。

### 3.7 菜单构建期性能预算（**硬约束**）

资源管理器在**UI 线程**上同步调用我们的 `GetTitle` / `GetIcon` / `GetState` / `EnumSubCommands`。官方原文警告：*"Keep menu-construction methods fast. Do not perform expensive work on the File Explorer UI path."*

因此规定：

| 规则 | 说明 |
| --- | --- |
| 菜单构建期**禁止** | `CreateProcess(git.exe)`、任何网络访问、读取大文件、同步等待常驻进程超过预算 |
| 菜单构建期**允许** | 读进程内缓存、读共享内存/小 JSON 缓存、沿父目录向上查找 `.git`（限深度 + 进程内 LRU） |
| 预算 | 上述 4 个方法合计 **≤ 10 ms**；DLL 首次加载 **≤ 5 ms** |
| `Invoke` 里才做重活 | 全部 Git 操作都在 `Invoke` 之后异步进行 |
| `DllMain` 内**零逻辑** | 不做 COM 注册、不做 I/O、不创建线程 |

### 3.8 现代菜单独占的代价（必须明确承认的缺口）

选择 D1（只做现代菜单）后，以下场景**我们的菜单不可见**：

| 缺口 | 影响 | 缓解 |
| --- | --- | --- |
| **"显示更多选项"里没有我们** | 习惯用传统菜单的用户/企业策略环境下找不到入口 | 文档明示；M0 后评估"可选的传统注册表开关"（成本极低，仅需几条注册表项 + 命令行调用，不需要额外 DLL） |
| **第三方文件管理器不可见** | Total Commander / Directory Opus / xplorer² 等**只支持传统菜单**，不实现 Win11 现代菜单 | 同上。注意 xplorer² 作者公开批评"忽视第三方文件管理器"的做法 |
| **驱动器根目录**（`C:\`） | 无法提供"在此打开终端" | ⚠️待实测后决定；若无解，引导用户进入任意子文件夹使用空白处菜单 |
| **Win10 及更早** | 完全不支持 | 明确声明最低支持版本（§7.2） |

> 建议：即便 D1 不变，也把"传统菜单兼容开关"列为 M3 的可选增强，并向用户说明"仅影响第三方文件管理器与「显示更多选项」，不改变现代菜单体验"。

### 3.9 图标覆盖（overlay icons）不可用

- 图标覆盖处理器**必须**是 Explorer 进程内的传统 Shell 扩展；Sparse Package 路线对外提供的扩展点主要是上下文菜单、属性处理器、缩略图/预览处理器，**覆盖图标处理器不在其中**（⚠️待实测：官方 sparse package 文档的"支持的扩展点"清单未逐项列全，M0 用最小实验确认，结论写入《支持矩阵》）。
- 即使走传统路线，Windows 全系统**只有 15 个覆盖图标槽位**，TortoiseGit 等已占据部分。

**替代方案（v1）**：

1. 菜单项图标反映状态（干净/有改动/冲突）——通过 `GetIcon` 返回不同图标实现。
2. 主程序提供**状态列视图 / 仪表盘**（多仓库一览）。
3. 资源管理器的**详细资料列**需要属性处理器（同样属传统路线），**v1 不做**，列入 v2 评估。

### 4.3 复选（开关）与参数（`--flags`）交互规范

这是 D2 的核心，需要三层表达力：

> **菜单形态（产品决策，2026-09-24 v0.5 终稿）**：资源管理器右键菜单里**只有一个可点的「GitRT」**——
> 没有子菜单、没有分组、没有命令列表。**点击它 = 打开 GitRT 主窗口**（并把窗口的仓库/目录上下文
> 切到你右键的位置）。所有"选哪个命令、带什么参数"都在 GUI 里完成（完整命令列表 + 参数面板 + 状态面板 +
> AI 助手）。这样做的理由：右键菜单天然受 16 项上限、层级深度和平铺宽度限制，而**命令表有 32 条**；
> 把选择权放回窗口既不受限、又能显示状态与预览。
>
> 分层菜单（GitRT → 8 个分组 → 命令）没有删掉，而是作为**可配置能力**保留：`"menu.mode": "tree"`
> 即可切回（配合 `menu.directTop` / `menu.showFlags`），供偏好右键直达的用户使用。

**层级 1 — 复选开关（仅 `menu.mode=tree` + `menu.showFlags=true` 时在菜单内直接反映状态）**
`IExplorerCommand::GetState` 原生支持复选框：

| 值 | 含义 |
| --- | --- |
| `ECS_ENABLED (0x0)` | 可用 |
| `ECS_DISABLED (0x1)` | 灰显 |
| `ECS_HIDDEN (0x2)` | 隐藏（用于按场景裁剪命令） |
| `ECS_CHECKBOX (0x4)` | 显示为复选框（未勾选） |
| `ECS_CHECKED (0x8)` | 显示为复选框（已勾选，总是与 `ECS_CHECKBOX` 同时返回） |
| `ECS_RADIOCHECK (0x10)` | 单选组（Win7+） |

用途与规则：

- **默认关闭**：菜单保持"分组 → 命令"两层结构，最干净；开关在参数面板里按调用选择。
- **开启后**（`"menu.showFlags": true`）：开关出现在对应命令下方的分隔符之后，点击 = 立即切换配置并落盘，**不执行任何 Git 操作**（例如"拉取时使用变基"）。
- **状态必须来自配置缓存**，不能在 `GetState` 里现算（§3.7）。
- **单选组**用于互斥选项：终端类型（Git Bash / PowerShell / Windows Terminal）、重置模式（soft/mixed/hard）、拉取策略（merge/rebase/ff-only）。
- 复选项**必须在菜单文字上可自解释**，例如「拉取 · 使用变基 (--rebase)」而非「变基 ✓」。

依据：[\_EXPCMDSTATE 枚举](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/ne-shobjidl_core-_expcmdstate)。

**层级 2 — 命令面板（参数输入）**
带参命令（表中"参数"列非空）点击后打开一个**轻量参数面板**（不是完整 GUI 窗口），内容：

```
┌─ 推送 ─────────────────────────────────────────────┐
│ 远端   [origin            ▾]   分支 [main        ▾] │
│ ☐ 强制推送（--force-with-lease）                     │
│ ☐ 推送标签（--tags）  ☑ 设置上游（--set-upstream）    │
│ ─────────────────────────────────────────────────── │
│ 等价命令（可复制 / 可在终端执行）：                   │
│ git push --set-upstream origin main                 │
│                                                     │
│        [复制命令]  [在终端执行]   [取消]  [执行]      │
└─────────────────────────────────────────────────────┘
```

设计要点：

- **实时预览等价命令行**——这是 Persona P2（CLI 熟练用户）留存的关键：菜单只是"命令构建器"，用户始终能看到、复制真实命令。
- 参数**预填智能默认值**：当前分支、`origin`、上次使用值（记忆最近 N 次）。
- **高级模式**：可展开直接编辑 `--flags` 原文（白名单校验，见 §5.7）。
- 危险操作的"执行"按钮需要二次确认（§4.6）。
- 面板尺寸小、键盘优先（Enter 执行、Esc 取消）、记住上次位置。

**层级 3 — 非交互降级（已实现，同时是自动化测试的地基）**
无 GUI 环境（自动化 / 远程会话 / CI）下，全部命令都可通过命令行调用，且与菜单点击走**同一条** `CommandSpec → BuildCommand → git_runner` 路径：

| 参数 | 含义 |
| --- | --- |
| `--run <command-key>` | 执行命令表中的一条命令（key 见 §4.2 对应实现） |
| `--ai "<自然语言>"` | 让 AI 规划一条命令（**默认只规划不执行**，见层级 4） |
| `--ai-run` | 与 `--ai` 连用：通过闸门后真的执行 |
| `--dry-run` | 只构造 argv 不执行（契约测试用） |
| `--list-commands` | 导出命令表（key / 分组 / 是否需仓库 / 执行类型 / 参数 / 选项），供测试与 CI 消费，避免测试硬编码命令清单 |
| `--cwd <dir>`、`--paths "p1;p2"`、`--param k=v`、`--flag k[=v]` | 上下文与参数 |
| `--out <file>` | 结果报告写入文件（脚本可靠读取；避免依赖控制台） |

退出码约定：`0` 成功 · `1` 构造/校验失败 · `2` git 执行失败 · `3` 用法错误 · `4` AI 调用失败 · `5` AI 认为没有合适命令。

> 注意：`GitRT.exe` 是 GUI 子系统程序，脚本里直接 `& GitRT.exe …` **不会阻塞等待**；请用 `Start-Process -Wait`，或直接读 `--out` 报告。

**层级 4 — AI 助手：自然语言 → 命令（v0.2 新增，已实现）**

目标：让"知道自己要干什么、但不记得 git 怎么打"的用户也能完成操作，**同时不引入"AI 把命令直接敲进 shell"这类不可控风险**。

```
┌─ GitRT AI 助手 ─────────────────────────────────────────────────────────┐
│ 配置: https://api.deepseek.com/chat/completions · deepseek-chat          │
│       · Key(DEEPSEEK_API_KEY): 已设置 ✓                                  │
│ 用自然语言描述你要做的事                                                  │
│ 例如：把当前所有改动提交，然后推送到 origin                                │
│ ┌─────────────────────────────────────────────────────────────────────┐ │
│ │ 把当前改动提交并推送                          （用户输入）             │ │
│ └─────────────────────────────────────────────────────────────────────┘ │
│ [生成方案] [执行方案] [复制命令] [关闭]                                    │
│ AI 生成的方案（已通过白名单校验）                                          │
│   命令: sync.push (推送…)                                                │
│   选项: set-upstream                                                     │
│   说明: 推送当前分支并设置上游                                             │
│   ── 即将执行的命令：git push --set-upstream                             │
│ 运行结果                                                                 │
│   ── 完成（exit=0, 412 ms）──                                            │
│    <git 输出尾部>                                                        │
│ 详情（AI 原始回复）                                                       │
└─────────────────────────────────────────────────────────────────────────┘
```

**安全闸门（不可协商，必须实现）**

1. AI **只**输出结构化计划 `{"command":"<命令表内的 key>","params":{…},"flags":{…},"explanation":"…"}`，**禁止**输出命令行文本，更禁止执行任何 AI 生成的字符串。
2. 计划必须经 `PlanToCommand()` 走与菜单/参数面板**完全相同**的校验与 argv 构造：命令 key 必须在命令表内；选项 key 必须在 `FlagSpec` 白名单内；参数名必须是该命令声明的 `paramKey`；否则**拒绝执行**并把原因显示给用户。
3. 未登记选项**忽略并提示**（不报错、不猜测）；Internal（GUI 交互）命令不允许由 AI 执行；需要仓库的命令在未选仓库时拒绝。
4. 命令本身 ⚠️危险 或勾选了危险选项时，**必须再弹一次模态确认**（默认按钮为"否"）。
5. **没有"自动执行"开关**：无论什么配置，AI 方案都必须由用户点「执行方案」才会真正运行。
6. 每次生成的等价命令行**必须可见、可复制**（与层级 2 完全一致）。
7. 校验失败、网络失败、模型返回表外命令时：**不产生任何 git 调用**。

**配置与降级**

- 默认 provider：**DeepSeek**（`https://api.deepseek.com/chat/completions`，`deepseek-chat`）；因为走 OpenAI 兼容协议，可改为任意兼容端点（OpenAI / 本地 Ollama / LM Studio / 企业网关）——这也是"不绑定单一厂商"的实现方式。
- API Key **只从环境变量读取**（默认 `DEEPSEEK_API_KEY`，变量名可配置），**不写入配置文件、不落盘、不进日志**。
- 未配置 Key 时明确提示"请设置环境变量 X 后重启"，并显示当前 endpoint / model / 配置文件路径；**绝不静默失败**。
- 模型上下文只附带：仓库路径、当前分支、已选文件名（≤20 项）；**不发送文件内容**。
- 系统提示词中的命令表由 `CommandTable()` **自动生成**，保证 AI 永远看不到与代码脱节的旧命令表。

**验收标准**：见 §8「已实现的测试地基」——AI 链路 11 项断言必须全绿，其中"伪造命令必须被拒绝（exit=1 + `plan_error`）且不发生任何 git 调用"是硬性门槛。

### 4.4 场景 × 菜单可见性矩阵

| 场景 | 可见入口 | 命令裁剪逻辑（`GetState` 返回 `ECS_HIDDEN`） |
| --- | --- | --- |
| 在 Git 仓库内的文件夹空白处 | `GitRT ▸` 全量（按优先级） | 隐藏"初始化仓库" |
| 在 Git 仓库内的文件夹上 | 全量 | 同上；"打开终端"用该文件夹 |
| 在**非** Git 仓库的空白处/文件夹 | 精简菜单 | 只留：初始化仓库、克隆到此处、打开终端、AI 助手、首选项 |
| 多选文件（仓库内） | 文件相关子集 | 只留：暂存/取消暂存/撤销改动/加入 .gitignore/差异/提交所选内容 |
| 单个文件 | 文件子集 + 历史/Blame | 同上 + 文件历史、Blame |
| 驱动器根目录 | ⚠️待实测 | 若不可注册，则不出现 |
| 仓库处于冲突/变基/合并中 | 全量 + **顶部状态提示项** | 增加"继续变基/合并"、"中止操作"等上下文命令 |
| 无 git.exe（PATH 缺失或未安装） | 仅 1 项 | 显示"未找到 git，点击安装/设置路径" |

**判定顺序**（`GetState` 内，纯本地、O(1) 级别）：选择类型 → 向上查找 `.git`（限深 12 层、进程内 LRU 缓存）→ 读内存状态缓存（判断冲突/操作中）→ 输出状态位。

### 4.5 关键流程

**流程 1：提交所选内容（P0 主流程）**

```
右键选中 2 个文件 → GitRT ▸ 提交
  → 参数面板（预填：最近提交信息风格、当前分支）
  → 用户输入 "fix: 修正登录跳转"
  → [执行] → 交常驻进程 → git add -A -- <2 files> → git commit -m ...
  → 进度窗口（若 > 1.5s）→ 成功通知（可点击查看提交详情）
```

**流程 2：失败与冲突的可恢复性**

任何操作失败必须满足三条：① 完整日志（可复制）；② **等价命令行**（用户可自己在终端重跑）；③ 明确"当前仓库处于什么状态"（例如"合并冲突未解决，可继续或中止"）。绝不出现"操作失败"四个字后无可行动信息。

**流程 3：凭据交互**（§5.6）
`git push` 需要密码时：子进程环境注入 `GIT_ASKPASS=GitRT.AskPass.exe`，由它弹原生小窗口收集凭据 → stdout 返回 → 优先交给 GCM 存储，本程序不落盘。

**流程 4：长操作进度**
`fetch/pull/push/clone/lfs` 可能持续数十秒。设计：常驻进程流式回传 `progress` 事件 → 进度窗口显示可读阶段（"解析增量 / 接收对象 43% / 解决差异"）+ 取消按钮（发送 SIGTERM 等价物并保留可恢复状态）。

**流程 5：状态刷新**
仓库文件变化 → 目录监视触发 → 常驻进程重算状态 → 更新共享内存缓存 → **不主动刷新资源管理器**（覆盖图标不做，无此需求）；菜单下次打开即读到新状态。

**流程 6：首次安装**
安装器写文件 → 注册 Sparse MSIX → **重启资源管理器**（必须，否则菜单不出现）→ 首次右键引导页（解释复选/参数面板用法）。

**流程 7：AI 助手（自然语言 → 命令 → 结果）**

```
用户输入"把改动提交并推送到 origin"
  → 校验 API Key（未配置则给出配置指引，终止）
  → 组装提示词：命令表（由代码生成）+ 仓库/分支/已选文件上下文
  → 工作线程 POST /chat/completions（UI 不阻塞，按钮置灰；可取消等待）
  → 取 choices[0].message.content → 解析为计划
  → PlanToCommand()：命令 key / 选项 / 参数 / 仓库 四重校验（安全闸门）
  → 界面显示：选中命令 + 参数 + 选项 + 警告 + 【等价命令行】
  → 用户点[执行方案]（危险操作再确认一次）
  → 与手动点击完全相同的执行路径 → 进度窗口流式输出（>1.5s 才显示）
  → 结束后把"运行结果"（退出码 + 输出尾部）回填到 AI 窗口
失败路径：表外命令 / 非 JSON / HTTP 错误 → 显示原因 + 禁用[执行方案]，不执行任何 git 命令。
```

### 4.6 危险操作分级与确认

| 级别 | 示例 | 确认策略 |
| --- | --- | --- |
| 安全 | 暂存、抓取、提交、查看 | 直接执行 |
| 谨慎 | 推送、合并、变基、切换分支 | 面板显示将影响的分支/远端；有未提交改动时警告 |
| ⚠️危险（不可逆） | 撤销改动、清理未跟踪、重置 `--hard`、删除分支/标签、`push --force*` | **二次确认** + 明确写出将被丢弃的内容（文件清单/提交数）+ 对可保留者默认先创建备份（`stash` 或 reflog 提示） |

**原则**：宁可多点一次，也不静默丢数据。对 `push --force` 提供 `--force-with-lease` 为默认（更安全），强行 `--force` 需要额外勾选。

**AI 生成的方案同样受本节约束**：危险度不由"谁生成的"决定，而由命令本身与所勾选项决定；AI 方案命中 ⚠️危险 时必须走同一套二次确认，且**任何情况下都不会自动执行**。

### 4.7 配置与个性化

- **全局配置**：`%APPDATA%\GitRT\config.json`（界面语言、终端偏好、菜单项显隐、复选默认值、日志级别、**AI 端点/模型/Key 变量名**）。
- **AI 凭据**：**只从环境变量读取**（默认 `DEEPSEEK_API_KEY`），配置文件里只保存"变量名"而非 Key 本身；v2 再评估用 CredWrite(DPAPI) 存 Key 以方便非技术用户（见 Q11）。
- **仓库级配置**：写入用户自己的 Git 配置命名空间 `git config --local gitrt.*`（**随仓库走、可 diff、可被团队共享**），例如 `gitrt.defaultPullStrategy=rebase`、`gitrt.hideDangerousCommands=true`。
- **不覆盖用户既有 Git 配置**：只读 + 新增 `gitrt.*` 命名空间；任何修改 git config 的动作都必须在 UI 上显式展示。
- **菜单裁剪**：用户可隐藏不用的分组（例如 P3 半技术用户隐藏"高级"整个分组）——这是缓解 §3.6 条目上限的产品手段。

## 5. 系统架构

### 5.1 进程拓扑

```
┌─────────────────────────────────────────────────────────────┐
│ Explorer.exe（资源管理器，UI 线程）                             │
│   └─ GitRT.Shell.dll   ← IExplorerCommand                     │
│        · 只读缓存、零 Git 调用、零网络、DllMain 无逻辑           │
│        · GetState/GetTitle/GetIcon/EnumSubCommands ≤ 10ms      │
└──────────────┬──────────────────────────────────────────────┘
               │ ① 命名管道（首选，≤200ms 超时）
               │ ② 降级：直接 CreateProcess（常驻不可用时）
               ▼
┌─────────────────────────────────────────────────────────────┐
│ GitRT.Broker.exe（常驻，每用户会话一个）                        │
│   · 状态缓存（repo → status）＋ 目录监视（ReadDirectoryChangesW）│
│   · 任务队列、进度聚合、通知                                │
│   · 启动/复用 GUI 窗口                                       │
└───────┬───────────────────────────────┬──────────────────────┘
        │                               │
        ▼                               ▼
┌────────────────────┐        ┌──────────────────────────────┐
│ GitRT.exe（GUI）    │        │ git.exe（外部真相源）          │
│ 日志图/差异/历史/    │◀──────▶│ CREATE_NO_WINDOW             │
│ 参数面板/进度窗口    │        │ 命名管道 stdio / GIT_REDIRECT │
└────────────────────┘        └──────────────────────────────┘
        ▲
        │ 凭据
┌────────────────────┐
│ GitRT.AskPass.exe  │  ← GIT_ASKPASS / SSH_ASKPASS
└────────────────────┘
        │
   （可选）libgit2 1.9.7 —— 仅只读快路径（§5.4）
```

**为什么必须三层（而不是一个 DLL 干完）**：

> ⚠️ 上图把 DLL 画在 `Explorer.exe` 内，这是**最坏情况**（也应按此设计）。打包的菜单处理器是否可能由代理进程（`dllhost.exe`）承载，属 §3.10 的 S5 待实测项；实测结论会同时影响本节的崩溃隔离论证与 §7.4 的可靠性要求。

1. **Explorer 线程不可阻塞**（§3.7 硬约束）。
2. **崩溃隔离**：DLL 内的任何缺陷都不应拖垮资源管理器——DLL 保持极小、只读缓存、无第三方依赖。
3. **架构与权限边界**：DLL 位于 `Program Files`、随 MSIX 身份包注册；GUI/Broker 可以独立更新，不必重新注册身份包（§3.2）。
4. **32/64/ARM64 宿主兼容**（未来第三方文件管理器场景）。

### 5.2 模块职责

| 模块 | 语言 | 职责 | 硬性约束 |
| --- | --- | --- | --- |
| `GitRT.Shell.dll` | C++20 | 菜单枚举、状态位、图标、`Invoke` 只做"转发" | ≤ 400KB、无第三方依赖、静态链接运行时、无 `DllMain` 逻辑 |
| `GitRT.Broker.exe` | C++20 | 状态缓存、目录监视、任务调度、IPC 服务端 | 内存 ≤ 60MB、空闲 CPU ≈ 0 |
| `GitRT.exe` | C++20 | 参数面板、进度窗口、提交图、差异、历史、Blame、设置 | 冷启动 ≤ 400ms |
| `GitRT.AskPass.exe` | C++20 | 凭据收集（极小，无 GUI 框架依赖） | 必须能在无控制台环境工作 |
| `GitRT.Core`（静态库） | C++20 | 命令模型、flags 校验、git 进程封装、配置、日志 | 被上述所有模块复用；**Shell.dll 只用到极小子集** |

### 5.3 IPC 设计

- **通道**：命名管道 `\\.\pipe\GitRT.<SID>`；管道 ACL 仅当前用户；服务端校验客户端 PID/令牌，拒绝非本用户连接。
- **协议**：长度前缀 + 紧凑二进制（或 JSON，日志/调试用文本、热路径用二进制）。
- **请求**：`{reqId, op, cwd, selection[], flags{}}`。
- **响应**：流式事件 `{reqId, type: progress|log|prompt|done|error, payload}`。
- **超时与降级**：菜单构建期查询超时 **200ms** → 降级为"状态未知"（菜单照常显示，状态相关条目标注"计算中"）；`Invoke` 后无响应 → 直接 `CreateProcess` 兜底，保证功能可用。
- **版本协商**：握手携带协议版本，DLL 与 Broker 版本不匹配时以 DLL 为准降级（避免升级后 Explorer 里旧 DLL 找不到新 Broker 导致菜单消失）。

### 5.4 Git 后端策略与一致性规则

**默认（也是唯一真相源）：`git.exe` CLI。**

理由（均有出处，详见调研材料）：

1. **libgit2 官方定位就不是替代 git**：其 README 明确表示不打算替代 git 工具/面向用户的命令，许多命令"超出本库直接实现的范围"。
2. **功能缺口会造成行为不一致**：libgit2 不执行 **hooks**；不支持 **interactive rebase**；不支持 **sparse-checkout / partial clone（promisor）**；**SHA-256 仍为实验**；外部 merge driver 不生效。
3. **性能反而是 CLI 占优**：libgit2 的 `git_status_list_new` 在大型仓库上比 `git status` 慢 **2.5–6 倍**（其 issue #4230 至今未解决），原因是未实现 `core.untrackedCache` / `core.fsmonitor`、`.gitignore` 匹配不缓存、`lstat` 用法次优。starship 已因性能问题把 git2 换回 CLI 调用。
4. **零额外负担**：本机已有 MSYS2 UCRT64 的 libgit2 1.9.7 可链接，但"能用"不等于"该用"。

**只读快路径（可选，P2 之后）**：差异预览、日志渲染、Blame 等可用 libgit2 降低进程开销，但必须满足：

- 结果与 CLI **可见一致**（同一 config 解析、同一 ignore 规则）；
- 遇到**任何**不支持特性（partial clone / sparse-checkout / SHA-256 / 工作树）**自动回退 CLI**；
- 诊断信息里标注实际使用的后端（便于排错与用户信任）。

**统一的 git 调用规范**（无论哪个后端）：

```
可执行文件：git.exe（优先取配置路径，其次 PATH，最后提示用户）
状态查询：  git --no-optional-locks -c core.quotepath=false \
                status --porcelain=v2 -z --branch --show-stash
环境变量：  GIT_TERMINAL_PROMPT=0
            GIT_PAGER=cat
            GIT_ADVICE=0
            GIT_CEILING_DIRECTORIES=<盘符根/网络边界>   ← 防止向上遍历慢网络目录
            GIT_ASKPASS / SSH_ASKPASS = GitRT.AskPass.exe
进程标志：  CREATE_NO_WINDOW（0x08000000）
stdio：     优先命名管道 + GIT_REDIRECT_STDIN|STDOUT|STDERR
            次选匿名管道（注意可继承句柄问题）
路径传参：  一律 argv 数组 + `--` 终止符，永不拼接 shell 字符串
```

另建议用户在设置里**一键开启** `core.untrackedCache=true` 与 `core.fsmonitor=true`（Windows/macOS 内置 daemon），并说明"首次查询会预热、之后显著变快"。

### 5.5 状态观察者与缓存

参考 TortoiseGit 的 `TGitCache.exe`（后台计算状态、供 Shell 扩展查询、监视已见目录）与 gitstatusd 的思路，但**不复用其代码**（gitstatusd 为 GPL-3.0、无原生 Win32 构建、作者已声明仅极小维护）。

| 层 | 内容 | 失效策略 |
| --- | --- | --- |
| L1 进程内（DLL） | `repoPath → {head, dirty, staged, conflicts, opState}` 极简结构 | 由 Broker 推送更新（共享内存/管道） |
| L2 Broker 内存 | 完整状态 + 文件级明细 + 最近访问的目录集合 | 目录监视 + TTL（默认 3s）+ 手动刷新 |
| L3 磁盘 | `%LOCALAPPDATA%\GitRT\cache\<repo-hash>.bin`，含 mtime 校验 | 冷启动先用旧值（标注"可能过期"），后台校准 |

**冷启动策略**：没有任何缓存时，菜单仍然显示（只依赖 `.git` 存在性判断），状态类条目退化为"状态未知/点击计算"。**不允许**为了状态而阻塞菜单。

### 5.6 子进程与凭据

- 凭据**优先交给 Git Credential Manager**（GCM 在 Windows 默认使用 Windows 凭据管理器；存的是凭据/OAuth 刷新令牌，不是密码；MIT 许可，与 D3 兼容）。
- 需要非 HTTP 交互时（GCM 弹窗不受控的场合），实现 `GitRT.AskPass.exe` 作为 `GIT_ASKPASS`/`SSH_ASKPASS`——这是 TortoiseGit 的既有做法（其架构文档指出从 GUI 启动时没有 attached terminal，`git.exe`/`ssh.exe` 无法直接询问凭据）。
- **绝不**：明文落盘密码；使用 `credential.helper=store`；自研加密。
- 若必须自行保存（例如记住"最近仓库的 SSH passphrase"，v2 才考虑）：仅用 `CredWriteW`（Windows 凭据管理器）或 DPAPI `CryptProtectData`；注意 **DPAPI 的 `PromptStruct` 交互流程已弃用并将在 2027-02 移除**，新代码不得使用。

### 5.7 安全模型

| 威胁 | 缓解 |
| --- | --- |
| 参数注入 / 路径含空格引号 | 一律 argv 数组 + `--` 终止符；不做字符串拼接；`--flags` 走**白名单**（每个命令声明可用 flag 集合） |
| 不受信任仓库（克隆来的恶意 `.git`） | Git 自身规定"在不受信任来源的 `.git` 中执行命令不安全"（config/hooks 会被执行）。本产品：**只读查询与写操作分级**；写操作前做 `safe.directory` 检查并提示；默认不自动执行任何会触发 hook 的动作（无法阻止 git 执行 hook，但必须让用户知情） |
| 其他进程伪造 IPC 请求 | 管道 ACL 限当前用户 + 校验客户端令牌/PID |
| 提权面 | DLL 与 Broker **不需要管理员**；全机安装（写 `Program Files`、注册包）才需要 UAC |
| 日志泄露凭据 | 日志脱敏：剥离 URL 中的 userinfo、不记录 token/密码、不落盘 askpass 输入 |
| 崩溃影响宿主 | Shell DLL 极小化 + 全程异常边界（每个 COM 方法 `try/catch(...)`） |
| **AI 输出被当成命令执行**（提示注入 / 幻觉） | **AI 从不产出命令行，只产出"命令 key + 参数 + 选项"**；经命令表/`FlagSpec` 白名单/`paramKey` 三重校验后才由本程序构造 argv（§4.3 层级 4）；表外命令一律拒绝；无自动执行开关；危险操作二次确认 |
| AI 请求泄露仓库信息 | 只发送路径、分支名与选中文件名（≤20），**不发送文件内容**；端点可配置为本地模型；配置中不保存 API Key（只保存变量名） |

#### 5.8.2 MinGW-w64 写 Shell 扩展的已知坑（必须在 M0 验证）

| 坑 | 应对 |
| --- | --- |
| COM 导出名被修饰 | 用 `.def` 文件显式导出 `DllGetClassObject` / `DllCanUnloadNow` / `DllRegisterServer`（可选），或 `extern "C"` + `--kill-at` |
| 无 ATL/WRL（MSVC 生态） | 自写轻量 `ComPtr` 与 COM 样板；不引入只能 MSVC 编译的库 |
| 无 `__try/__except`（SEH） | 用 `try/catch(...)` + `SetUnhandledExceptionFilter` + 可选 VEH；**关键**是保证异常不跨 COM 边界 |
| C++ 异常跨模块边界 | 每个 COM 方法都要 catch 所有异常并转为 `HRESULT` |
| 运行时库 | Shell DLL 静态链接 `libstdc++/libgcc`（`-static-libgcc -static-libstdc++`），避免为 Explorer 引入 DLL 依赖；DLL 体积与加载时间同时受益 |
| 架构匹配 | DLL 位宽必须与加载它的 Explorer 一致；ARM64 可用 MSYS2 `clangarm64` 环境交叉构建 |
| 缺 `/GS`、CFG 等 MSVC 加固 | 靠"极简 DLL + 严格测试 + 崩溃注入"补偿 |
| 清单嵌入 | `windres` 编译 `.rc`，其中包含 ① 通用控件 v6 依赖清单 ② **内嵌 `msix` 身份元素**（§3.4） |
| 若 MinGW 路线受阻 | 保持 CMake 双工具链能力，切 MSVC（需装 VS Build Tools）——**这是 S1 的备选方案** |

#### 5.8.3 MSIX 打包流水线（Sparse Package）

```
packaging/
├─ AppxManifest.xml              # 由 packaging/identity.json 生成，避免手改不一致
├─ Assets/                       # 必需图片（AppListEntry=none，图片仅需存在）
└─ build.ps1                     # 打包 + 签名 + 注册（开发/发布两种 profile）

步骤：
1) makeappx.exe pack /o /d sparsePack /nv /p GitRT.msix      # /nv 必需（跳过文件校验）
2) signtool.exe sign /fd SHA256 /f <cert.pfx> /tr <ts> /td SHA256 GitRT.msix
   （开发机：自签名 + 导入 .cer 到 Cert:\CurrentUser\TrustedPeople；发布：SignPath/OV）
3) Add-AppxPackage -Path GitRT.msix -ExternalLocation "C:\Program Files\GitRT"
4) 重启资源管理器（安装/升级后必须，否则菜单不出现）
卸载：Get-AppxPackage GitRT | Remove-AppxPackage   ← 必须在独立 powershell 进程执行
```

> `packaging/identity.json` 作为 `publisher / packageName / applicationId / version` 的**单一真相源**，同时供 ① `AppxManifest.xml` ② DLL 内嵌的 `msix` 清单 ③ 安装器 三处使用。这是对 §3.4 那个"损失 4–5 天"的坑的工程化防御。

### 5.9 日志与诊断

- 日志：`%LOCALAPPDATA%\GitRT\logs\`，按天滚动、默认 INFO、可切 DEBUG；含每次 git 调用的**完整 argv + 退出码 + 耗时**（凭据脱敏）。

- **"重新注册 Shell 扩展"**：卸载重装身份包 + 重启资源管理器的封装动作（安装/升级失败时的自救入口）。

### 7.4 可靠性

- 任何 Git 操作失败：有日志、有等价命令行、有仓库状态说明（§4.5 流程 2）。
- Broker 崩溃：DLL 自动降级直连，功能不中断，下次操作自动重启 Broker。

### 附录 C：本仓库现有资产处置

当前仓库除 `.git` 外只有一个文件：`tools/Set-NewMenuItems.ps1`（约 7.9KB），功能是**精简「右键 → 新建」子菜单**（把 `ShellNew` 键改名为 `ShellNew.disabled`，可还原）。

问题：该脚本第 26–27 行引用 `$here\..\lib\Common.ps1` 与 `$here\..\lib\Menu.ps1`，**这两个文件在仓库中不存在**，因此脚本当前**无法运行**。

建议（需负责人确认，见 Q8）：

1. 它属于"注册表菜单"路线，与 D1（只做现代菜单）不同，因此**不是本产品的组成部分**；
2. 但它的"探测 → 备份 JSON → 改名 → 可还原"模式是很好的设计参考，可迁移为 GitRT 的"身份包安装/卸载 + 状态备份"思路；
3. 建议将其移入 `tools/legacy/` 并加 README 说明"未完成原型、缺 lib 依赖"；或在后续补齐 `lib/` 后作为独立工具保留。

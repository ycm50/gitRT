## 1. 已核实的实现前置事实

这些不是推测，是在本机实际检查得到的结果，直接决定实现写法。

| 事实 | 检查方式 | 对实现的影响 |
| --- | --- | --- |
| `shobjidl.h` 已含 `IExplorerCommand` / `IExplorerCommandState` / `IExplorerCommandProvider` / `IEnumExplorerCommand` 及 `IID_*`、`EXPCMDSTATE`、`EXPCMDFLAGS` | 读 `A:\msys64\ucrt64\include\shobjidl.h`（L1429–29352） | **MinGW 编译层无缺口**；头文件是 `shobjidl.h`（**不是** `shobjidl_core.h`，该文件在 UCRT64 中不存在）→ `#include <shobjidl.h>` |

| `IID_IExplorerCommand = {a08ce4d0-fa25-44ab-b57c-c7b1c323e0b9}`；`IID_IExplorerCommandState = {bddacb60-7657-47ae-8445-d23e1acf82ae}`；`IID_IExplorerCommandProvider = {64961751-0835-43c0-8ffe-d57686530e64}` | 同上 L28801 / L28968 / L29264 | 手写 `QueryInterface` 时用这些常量，不自行发明 |

### 2.2 产物与目标依赖图

```
core (STATIC: gitrt_core)
 ├─► shell    (SHARED: GitRT.Shell.dll)  ← 只链接 core 的【极小子集】(path_util/repo_probe/clsid/ipc 编解码)
 ├─► broker   (WIN32 EXE: GitRT.Broker.exe)
 ├─► gui      (WIN32 EXE: GitRT.exe)
 └─► askpass  (WIN32 EXE: GitRT.AskPass.exe)

测试: grt_unit_tests (链接 gitrt_core)
打包: build/GitRT.msix  ← packaging/AppxManifest.xml + Assets
```

**约束（架构强制）**：`shell` 目标**不得**链接 `config` / `git_runner` / `porcelain_v2` / `log` 的完整实现。做法是把 core 拆成两个静态库：

| 库 | 内容 | 允许被 shell 链接 |
| --- | --- | --- |
| `gitrt_core_tiny` | `win_prelude` `hr` `utf` `path_util` `repo_probe` `ipc`(解码) `clsid` | ✅ |
| `gitrt_core` | 上述 + `git_runner` `command_*` `porcelain_v2` `git_error` `config` `log` `precheck` `progress_parse` | ❌（仅 broker/gui/askpass） |

这样即使将来有人误加代码，**链接期就会失败**，比代码评审更可靠。DLL 体积由 §2.4 的 flag 组合保证。

### 2.3 顶层 CMake（施工图）

> **实现现状（2026-09-26 校对）**：下面是**最初的施工图**，落地时有意偏离了几处。
> 其中**版本号那一条必须按实现为准**——照抄会重新引入已修掉的缺陷：
>
> - **版本号只有一个来源**（`packaging/identity.json`）：`project()` **不再写 `VERSION`**，
>   `GRT_VERSION` 由 `GRT_ID_VERSION` 派生。此前它同时写在 `project(VERSION 0.1.0)`、
>   `GRT_VERSION="0.1.0"`、GUI 的 `resources.rc`、Shell 的 `.rc.in`、`identity.json` 五处，
>   已经漂成「0.1.0 vs 0.1.0.0」（见 §16.6）。
>   `identity.json` 还登记进了 `CMAKE_CONFIGURE_DEPENDS`：否则改了它不会重新 configure，
>   清单/资源/`clsid_values.h` 会停在上一次的产物上。
> - 未启用 `-Wpedantic`；告警门禁是 `GRT_WERROR`（CI 开、本地默认关）。
> - 未建 `src/broker` / `src/askpass`（下一增量）；测试目录是 `src/tests`（不是 `tests/`）。
> - 以源码为准：[CMakeLists.txt](../CMakeLists.txt)、[cmake/identity.cmake](../cmake/identity.cmake)。

**shell 目标（最关键的一段）**

```cmake
# src/shell/CMakeLists.txt
add_library(gitrt_shell SHARED
  dllmain.cpp class_factory.cpp explorer_command.cpp enum_commands.cpp
  selection.cpp snapshot_reader.cpp broker_client.cpp
  gitrt_shell.rc shell_strings.rc)

target_include_directories(gitrt_shell PRIVATE ${CMAKE_SOURCE_DIR}/src/core)
target_link_libraries(gitrt_shell PRIVATE gitrt_core_tiny ole32 oleaut32 shlwapi uuid advapi32)

# MinGW 默认给 DLL 加 "lib" 前缀 → 必须去掉，否则清单 Path 与实际文件名不一致
set_target_properties(gitrt_shell PROPERTIES
  PREFIX "" OUTPUT_NAME "GitRT.Shell"
  LINK_DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/gitrt_shell.def")

target_link_options(gitrt_shell PRIVATE
  -static -static-libgcc -static-libstdc++      # 不向 Explorer 引入运行时 DLL 依赖
  -Wl,${CMAKE_CURRENT_SOURCE_DIR}/gitrt_shell.def
  -Wl,--enable-auto-image-base
  -Wl,--nxcompat -Wl,--dynamicbase -Wl,--high-entropy-va   # 加固（MSVC 的 /GS 不可用）
  $<$<CONFIG:Release>:-s>)                       # Release 剥符号，减小加载时间

add_custom_command(TARGET gitrt_shell POST_BUILD
  COMMAND ${CMAKE_COMMAND} -E echo "== 导出表校验（期望仅 2~4 个符号）=="
  COMMAND objdump -p "$<TARGET_FILE:gitrt_shell>" | grep -A6 "Export Address Table" || true
  COMMENT "shell export table check")
```

> **导出表注意**：MinGW 的 `-shared` 在存在 `.def` 时的"是否自动导出全部符号"行为随 binutils 版本有差异。POST_BUILD 的 `objdump -p` 校验是**强制步骤**；若发现多余导出，追加 `-Wl,--exclude-all-symbols`。这一步必须在 M0 落地，否则会无意中把内部符号暴露给 Explorer 进程。

### 2.4 编译/链接 flag 备忘与理由

| flag | 作用 | 理由 |
| --- | --- | --- |
| `-fno-rtti` | 关闭 RTTI | 全部用 `static_cast` + 手写 `QueryInterface`；省掉类型信息表 |
| `-static -static-libgcc -static-libstdc++` | 静态运行时 | Shell DLL 绝不能依赖 `libstdc++-6.dll`/`libwinpthread-1.dll`（Explorer 加载时找不到即失败） |
| `-Wl,--nxcompat --dynamicbase --high-entropy-va` | ASLR/DEP | 替代 MSVC 的 `/DYNAMICBASE /NXCOMPAT` |
| `-mwindows` | GUI 子系统 | Broker / GUI / AskPass 必须无控制台窗口闪现（**不要**用 `CREATE_NO_WINDOW` 之外再依赖子系统） |
| `-municode` | 宽字符入口 | 若用 `wWinMain`/`wmain` 需要；GUI 用 `wWinMain` |
| `--codepage=65001` (windres) | UTF-8 `.rc` | 中文字符串与注释 |
| `-Wl,--kill-at` | 仅 32 位需要 | 32 位 `__stdcall` 名修饰；x64 无此问题（我们主目标 x64，保留备用） |

**已知不可用（MSVC 专属，必须绕开）**：`__try/__except`（SEH）、`/GS`、`/guard:cf`、ATL、WRL。

### 3.4 声明式命令表（`command_spec.h`）

**设计原则**：菜单标题、图标、可用性、flags 白名单、参数 schema、危险级别全部是**数据**，代码只做通用解释；这样新增命令 = 加一行表 + 一条 `git argv` 模板。

```cpp
// src/core/command_spec.h
namespace grt {

using CommandId = uint16_t;          // 见 §3.2
enum class GroupId : uint8_t { Repo, Commit, Sync, Branch, Inspect, Stash, Advanced, App, Separator };

enum class SelMask : uint8_t {       // 适用的右键场景（位掩码）
  None = 0, File = 1, Dir = 2, Background = 4, Multi = 8, Any = 0xFF
};

enum class Danger : uint8_t { Safe, Careful, Destructive };

enum class ParamKind : uint8_t {     // 参数面板需要收集什么
  None, Text, CommitMessage, BranchName, ExistingBranch, RemoteName, Revision,
  TagName, Url, Path, Pattern, Choice
};

enum class ParamSource : uint8_t {   // Choice/列表型参数的候选来源
  None, LocalBranches, RemoteBranches, AllBranches, Tags, Remotes, StashEntries, RemotesAndBranches
};

enum class ExecKind : uint8_t {
  Internal,      // GUI 内部动作（打开窗口/写配置/启动终端）
  Cli,           // 直接执行，无参数面板
  CliPanel,      // 先弹参数面板
  CliStream      // 长任务：流式进度 + 可取消
};

// flags 白名单中的一项
enum class FlagKind : uint8_t { Toggle, Radio, Value, Dangerous };
struct FlagSpec {
  const char*   key;          // 稳定 key，如 "rebase"（配置持久化用）
  const char*   gitArg;       // → "--rebase"
  FlagKind      kind;
  uint16_t      labelRes;     // 3000 段
  const char*   radioGroup;   // Radio 互斥组名，如 "pull-strategy"
  bool          defaultOn;
  bool          dangerNeedsSecondConfirm;  // 如 --force / --no-verify / -x
};

struct CommandSpec {
  CommandId     id;
  const char*   key;          // "sync.pull"（CLI/配置/日志）
  GroupId       group;
  uint16_t      titleRes;     // 2000 段
  uint16_t      descRes;      // 6000 段（工具提示）
  const char*   iconSpec;     // "GitRT.Shell.dll,-101" 或 IDI_*
  SelMask       applies;
  bool          requiresRepo; // false：非仓库场景也可用（init/clone/settings）
  Danger        danger;
  ParamKind     param;
  ParamSource   paramSource;
  ExecKind      exec;
  const FlagSpec* flags;      // 白名单（nullptr = 无 flag）
  uint8_t       flagCount;
};

// 全表（唯一定义点）
extern const CommandSpec kCommands[];
extern const size_t      kCommandCount;
const CommandSpec* FindCommand(CommandId id);
const CommandSpec* FindCommandByKey(std::string_view key);

} // namespace grt
```

### 3.6 菜单层级与 16 项预算的算法化处理

单层最多 16 项（产品文档 §3.6），而本表 38 条全部平铺会超限，因此菜单是**按组分层**的：

```
L0: GitRT                        (1 项，ECF_HASSUBCOMMANDS)
 └ L1: 8 个分组项 + 最多 8 个"高频直达项"
      ├ 高频直达（置顶，来自用户配置/使用频次）：提交所选内容、拉取、推送、状态面板 …
      └ 分组项：仓库 / 提交 / 同步 / 分支与标签 / 查看 / 储藏 / 高级 / 设置
           └ L2: 该组的命令（每组 ≤ 16 项；本表最大组 = 分支与标签 9 项 ✅）
```

**预算检查（编译期 + 运行时双保险）**：

```cpp
// compile-time: 静态断言每组不超过 16
static_assert(kMaxItemsPerLevel == 16);
// 运行期: MenuBuilder::Build() 若某层将超过 16 项，按 titleRes 排序后把溢出项
//         折叠进自动生成的 "更多…" 子菜单，并写一条 WARN 日志（doctor 会提示用户隐藏分组）
```

`ECF_ISSEPARATOR` 生成的纯分隔项**不计入** 16 项（依据社区实测），但我们仍在 builder 里统计"非分隔项"数量。

## 4. GitRT.Shell.dll 实现

### 4.1 COM 对象模型

```
DllGetClassObject(CLSID_GitRTCommand | IID_IClassFactory)
  └─ ClassFactory
       └─ CreateInstance → ExplorerCommand (根命令，实现 IExplorerCommand)
            ├─ GetTitle/GetIcon/GetToolTip/GetState/Invoke/GetFlags/GetCanonicalName
            └─ EnumSubCommands → EnumExplorerCommand
                                   └─ Next() → ExplorerCommand*(子命令)
                                                每个子命令同样实现 IExplorerCommand
                                                （自身可再 EnumSubCommands → 递归分层）
```

**关键设计**：**只用一个 C++ 类 `ExplorerCommand`** 承载所有层级的菜单项，用成员 `m_cmdId` 区分（根节点 `m_cmdId = 0`）。理由：子命令数量可达数十个且生命周期由 Shell 控制，单一类 + 工厂函数比多态继承更省代码、更好控制内存。

```cpp
// src/shell/explorer_command.h
namespace grt {

class ExplorerCommand final : public IExplorerCommand {
public:
  static HRESULT Create(CommandId cmdId, const SelectionContext& ctx, IExplorerCommand** out);

  // IUnknown
  IFACEMETHODIMP QueryInterface(REFIID, void**) noexcept override;
  IFACEMETHODIMP_(ULONG) AddRef() noexcept override;
  IFACEMETHODIMP_(ULONG) Release() noexcept override;

  IFACEMETHODIMP GetToolTip(IShellItemArray*, LPWSTR*) noexcept override;
  IFACEMETHODIMP GetCanonicalName(GUID*) noexcept override;
  IFACEMETHODIMP GetState(IShellItemArray*, WINBOOL, EXPCMDSTATE*) noexcept override;
  IFACEMETHODIMP Invoke(IShellItemArray*, IBindCtx*) noexcept override;
  IFACEMETHODIMP GetFlags(EXPCMDFLAGS*) noexcept override;
  IFACEMETHODIMP EnumSubCommands(IEnumExplorerCommand**) noexcept override;

private:
  ExplorerCommand(CommandId id, const SelectionContext& ctx);
  ~ExplorerCommand() = default;

  LONG                     m_ref = 1;
  CommandId                m_cmdId;
  SelectionContext         m_ctx;       // ★ 见 §4.4
  mutable std::wstring     m_titleCache; // GetTitle 可能被多次调用
  mutable EXPCMDSTATE      m_stateCache = ECS_ENABLED;
```

### 4.2 每个方法的实现与硬预算

所有方法**统一包裹**异常边界（MinGW 无 SEH，必须靠 `try/catch(...)`）：

```cpp
#define GRT_COM_TRY   try {
#define GRT_COM_CATCH } catch (const std::bad_alloc&) { return E_OUTOFMEMORY; } \
                      catch (...) { GRT_LOG_LAST_RESORT(); return E_FAIL; }

IFACEMETHODIMP ExplorerCommand::GetTitle(IShellItemArray* items, LPWSTR* name) noexcept
GRT_COM_TRY
  *name = nullptr;
  const auto* spec = FindCommand(m_cmdId);
  if (!spec) return E_INVALIDARG;
  // 资源加载：LoadStringW 命中缓存后为 O(1)
  std::wstring text = LoadCmdString(spec->titleRes);
  // 动态标题（如"提交 3 个文件…"）只在需要时拼接，且不触碰 git
  if (m_cmdId == kCommitId && m_ctx.fileCount > 1)
      text = FormatRes(6001, m_ctx.fileCount);
  return SHStrDupW(text.c_str(), name);      // ★ 必须用 SHStrDupW 分配
GRT_COM_CATCH
```

| 方法 | 实现要点 | 预算 |
| --- | --- | --- |
| `GetTitle` | `LoadStringW` + 极少量格式化；**不查 git**；结果缓存到 `m_titleCache` | ≤ 2 ms |
| `GetIcon` | 返回 `"GitRT.Shell.dll,-<res>"` 字符串（`LoadIcon` 由 Shell 做）；状态相关图标按快照 flags 选择不同资源 ID | ≤ 1 ms |
| `GetToolTip` | 静态资源字符串；含当前仓库根路径（来自 `m_ctx`，不查 git） | ≤ 1 ms |
| `GetCanonicalName` | 根节点返回 `GUID_GitRTCommandCanonical`，子命令返回 `GUID_NULL` | ≤ 0.1 ms |
| `GetState` | 见 §4.3 决策树；读共享内存快照（`OpenFileMappingW` 缓存句柄） | ≤ 5 ms **总计** |
| `Invoke` | 见 §4.5：写请求段 → 必要时启动 Broker → **立即返回** | ≤ 10 ms（不含目标进程启动） |
| `GetFlags` | 根节点与分组项返回 `ECF_HASSUBCOMMANDS`；复选项返回 `ECF_TOGGLEABLE`；分隔项 `ECF_ISSEPARATOR` | ≤ 0.1 ms |
| `EnumSubCommands` | 见 §4.4；构建 `std::vector<IExplorerCommand*>` 交给 `EnumExplorerCommand` | ≤ 5 ms |

> **必须返回 S_OK**：`GetState`/`GetFlags` 失败若返回非 S_OK，Shell 可能整项不显示。所有内部错误一律"降级为可用/可见 + 记日志"，只有参数非法才返回 `E_INVALIDARG`。

### 4.3 `GetState` 决策树（纯本地，无 git 调用）

```
输入：psiItemArray（可为 null）、fOkToBeSlow
1) 若 m_cmdId == 0（根节点）→ ECS_ENABLED（永远显示）
2) 从 m_ctx 取选择类型：
     - 无文件系统路径（虚拟项/库/网络根）→ ECS_HIDDEN
     - fileCount > kMaxSelection(200) → 仅保留"状态面板"，其余 ECS_DISABLED（灰显，附 tooltip 原因）
3) spec->applies 与 m_ctx.selMask 不匹配 → ECS_HIDDEN
4) spec->requiresRepo：
     - m_ctx.repoRoot 为空 且 该命令属于"非仓库可用"→ 继续
     - 否则 → ECS_HIDDEN
5) 读状态快照（SnapshotReader）：
     - 快照不可用（Broker 未运行/首次）→ 状态未知
          · 状态类命令（如"继续/中止操作"）→ ECS_HIDDEN
          · 其余命令 → ECS_ENABLED（乐观显示，点击后由 Broker 给出确切错误）
     - 快照可用 → 按 flags 判定：
          · 冲突中/变基中 → 隐藏普通命令，显示 branch.op 系列
          · 无暂存内容 → commit.commit 仍可见（点击后提示"无可提交内容"），
                           commit.unstage 隐藏
6) 复选项（spec->flags 中 kind==Toggle 的项）：
     - 返回 ECS_CHECKBOX | (配置值 ? ECS_CHECKED : 0)
7) 单选组（kind==Radio）：ECS_RADIOCHECK（选中者额外 | ECS_CHECKED）
8) 默认：ECS_ENABLED
```

**⚠️M0 待确认**：`GetState` 是否在 `EnumSubCommands` 之前被调用（决定 §4.4 的选择上下文能否复用缓存）。**设计上不依赖这个顺序**（见 §4.4）。

### 4.4 选择上下文捕获（**本产品最关键的实现细节**）

问题：`EnumSubCommands` **没有** `IShellItemArray` 参数，而子命令的 `GetState`/`Invoke` 都需要知道用户选中了什么。

方案（三层防御，缺一不可）：

```
① 缓存：ExplorerCommand 的 GetTitle/GetIcon/GetState/Invoke 任一次被调用时，
   把传入的 IShellItemArray 解析成 SelectionContext 并缓存到 m_ctx，
   同时（若是根节点/分组节点）通过 CopyToShared() 传给 EnumSubCommands 创建的子对象。
② 传递：EnumSubCommands 用父对象的 m_ctx 构造所有子命令。
③ 兜底：若 EnumSubCommands 先于任何带 array 的方法被调用（m_ctx 为空），
   子对象在自身 GetState/Invoke 收到 array 时**再解析一次**（幂等，代价可控）。
```

```cpp
// src/shell/selection.h
namespace grt {

struct ContextPath {                 // 一条规范化后的选择项
  std::wstring  path;                // 已去掉 \\?\ 前缀、已解析相对路径
  bool          isDirectory = false;
  bool          isFile = false;
  bool          isReparsePoint = false;   // 符号链接/junction：写操作前需再确认
  bool          inRepo = false;
};

struct SelectionContext {
  std::vector<ContextPath> paths;
  uint32_t      selMask     = 0;        // SelMask 位掩码
  uint32_t      fileCount   = 0;
  bool          truncated   = false;    // 超过 200 项被截断（仅用于显示）
  std::wstring  commonRoot;             // 选区公共父目录（用于"在此打开终端"）
  std::wstring  repoRoot;               // 探测到的仓库根；空 = 不在仓库内
  std::wstring  gitDir;                 // 可为 .git 目录或 worktree 的 gitdir
  RepoFlags     cheapFlags  = 0;        // ★ 廉价探测结果，见 §4.6
  bool          isNetwork   = false;    // UNC 路径
};

HRESULT ParseSelection(IShellItemArray* items, SelectionContext* out) noexcept;

} // namespace grt
```

**解析规则（`ParseSelection` 实现要点）**

| 情况 | 处理 |
| --- | --- |
| `IShellItem::GetDisplayName(SIGDN_FILESYSPATH)` 失败 | 标记"非文件系统项"，`selMask = 0` → 菜单隐藏 |
| 路径含 `\\?\` 前缀 | 去掉前缀后再参与显示；调用 Win32 前按需加回 |
| UNC（`\\server\share`） | `isNetwork = true`；**默认不做任何 git 状态查询**（配置可开启） |
| `.lnk` 快捷方式 | 不解析目标（避免"我右键的是快捷方式却操作了目标"的歧义）；写操作前在参数面板显式提示 |
| 多选混合（文件 + 文件夹） | `selMask` 同时置 `File\|Dir\|Multi`；子命令各自按 `applies` 过滤 |
| 选中数量 > 200 | `truncated = true`；仅允许"状态面板"等无路径命令 |
| 选区含仓库外路径 | `inRepo=false`；`Invoke` 前 `precheck` 会剔除并提示 |
| `psiItemArray == nullptr`（空白处） | `selMask = Background`；`commonRoot` 取 `GetCurrentDirectory` 不可靠 → 由 Shell 的 `IShellItem` 提供（空白处通常仍传入该目录的 item） |

> ⚠️M0 待确认：文件夹**空白处**右键时 Shell 传入的 item 是"该目录"还是"目录的父级"，直接影响 `Directory\Background` 语义。用探针日志（§4.8）实测记录。

### 4.5 `Invoke` 转发（不阻塞、不丢请求）

```
1) GrT_COM_TRY 包裹；任何异常 → E_FAIL 且写日志
2) 若 spec->exec == Internal 且需要 UI → 走 Broker 启动 GUI（同 §4.5.3）
3) 构造 Request 结构（§5.3），写入匿名/命名共享内存段：
     名称：Local\GitRT.Req.<新GUID>
     内容：{cmdId, ctx(paths), flags(配置), timestamp, callerPid, protocolVer}
4) 尝试连接管道 \\.\pipe\GitRT.<sid>.v1：
     - CreateFileW 成功（Broker 在运行）→ 发送一行 {"op":"invoke","section":"<name>"} 后立即关闭
     - 失败（Broker 未运行）→ CreateProcessW(GitRT.Broker.exe, "--request-section <name>", CREATE_NO_WINDOW)
5) 返回 S_OK（不等待任何结果）
6) 共享内存段由 Broker 打开并负责关闭；DLL 侧写完后 CloseHandle 即可（命名段在 Broker
   持有句柄期间仍然存在）
```

**失败模式与对策**

| 失败 | 现象 | 对策 |
| --- | --- | --- |
| Broker 启动失败（被杀软拦截/权限） | 点了没反应 | `Invoke` 内降级：直接 `CreateProcessW(GitRT.exe --run <key> --paths-file <name>)`；仍失败则弹最小 MessageBox 说明 |
| 共享内存段未及时被打开 | 请求丢失 | 段名带时间戳；Broker 启动时扫描 `Local\GitRT.Req.*` 前缀补收（**兜底机制**） |
| 用户连点多次 | 重复执行 | Broker 侧按 `{cmdId, pathsHash}` + 500ms 窗口去重 |

### 4.6 廉价文件系统探测（`repo_probe`）—— 菜单期状态的核心

**这是让"菜单期零 git 调用"成立的关键**：`.git` 目录下的若干文件/目录**存在性**足以判定绝大多数"操作中"状态。

```cpp
// src/core/repo_probe.h
namespace grt {

enum RepoFlag : uint32_t {
  RF_None            = 0,
  RF_IsRepo          = 1u << 0,
  RF_Worktree        = 1u << 1,   // .git 是文件（gitdir: 指向真实目录）
  RF_Submodule       = 1u << 2,   // .git 文件 + 父仓库（可选精确化）
  RF_Merging         = 1u << 3,   // MERGE_HEAD 存在
  RF_Rebasing        = 1u << 4,   // rebase-merge/ 或 rebase-apply/ 存在
  RF_RebaseInteractive = 1u << 5, // rebase-merge/interactive 存在
  RF_CherryPicking   = 1u << 6,   // CHERRY_PICK_HEAD
  RF_Reverting       = 1u << 7,   // REVERT_HEAD
  RF_Bisecting       = 1u << 8,   // BISECT_LOG
  RF_IndexLocked     = 1u << 9,   // index.lock 存在
  RF_DetachedHead    = 1u << 10,  // HEAD 内容不是 "ref: refs/heads/..."
  RF_ShallowRepo     = 1u << 11,  // shallow 文件
  RF_SparseCheckout  = 1u << 12,  // info/sparse-checkout 或 config 中 core.sparseCheckout
  RF_PartialClone    = 1u << 13,  // config 含 extensions.partialclone（→ 禁用 libgit2 快路径）
  RF_Network         = 1u << 14,  // 路径在网络位置（不做状态查询）
};

// 从 path 向上查找仓库根（限深 kMaxUpWalk = 12），返回探测结果
RepoFlags ProbeRepo(const std::wstring& path, std::wstring* repoRoot,
                    std::wstring* gitDir) noexcept;

} // namespace grt
```

**探测规则（每条都是 `GetFileAttributesW`/小文件读取级别）**

| 判定 | 检查 |
| --- | --- |
| `.git` 存在 | `GetFileAttributesW(dir + L"\\.git")`：`FILE_ATTRIBUTE_DIRECTORY` → 普通仓库；否则读取该文件首行 `gitdir: <path>` → worktree/submodule |
| 变基中 | `gitDir\rebase-merge\` 或 `gitDir\rebase-apply\` 存在；`rebase-merge\interactive` 存在 → 交互式 |
| 合并中 | `gitDir\MERGE_HEAD` 存在 |
| cherry-pick/revert | `gitDir\CHERRY_PICK_HEAD` / `REVERT_HEAD` |
| 二分中 | `gitDir\BISECT_LOG` |
| 索引被锁 | `gitDir\index.lock` 存在 |
| 分离头指针 | 读 `gitDir\HEAD`（< 100 字节），不以 `ref: ` 开头 |
| 浅克隆 | `gitDir\shallow` 存在 |
| 稀疏检出 | `gitDir\info\sparse-checkout` 存在 |
| 部分克隆 | 读 `gitDir\config`（< 64KB 上限），匹配 `extensions.partialclone`；**结果缓存**（config mtime 变化才重读） |

**性能**：一次 `ProbeRepo` ≈ 10–12 次属性查询 + 最多 2 个小文件读；在 NTFS 上通常 < 0.5 ms。DLL 内维护 `path → ProbeRepo 结果` 的 LRU（容量 64，键为目录路径），使同一目录反复右键接近 0 成本。

> **降级策略**：探测失败一律返回 `RF_None`（= 非仓库），菜单退化为"仅显示 init/clone/settings"。**绝不**在探测失败时猜测。

### 4.7 状态快照读取（`snapshot_reader`）

```cpp
// src/shell/snapshot_reader.h
namespace grt {

// 与 Broker 共享的内存布局（见 §5.2），只读
struct SnapshotSlot {
  uint64_t pathHash;      // FNV-1a(64) of 小写化后的仓库根路径; 0 = 空槽
  uint32_t rootLen;       // 调试用
  uint32_t flags;         // RepoFlag 位 + 状态位（见下）
  int32_t  ahead, behind; // repo vs upstream
  uint64_t updatedMs;     // GetTickCount64 基准
  uint32_t generation;    // 槽内一致性
  uint32_t reserved;
};

enum StatusFlag : uint32_t {
  SF_Known          = 1u << 0,   // 该槽已有有效状态
  SF_Dirty          = 1u << 1,   // 工作区有改动
  SF_Staged         = 1u << 2,   // 索引有改动
  SF_Untracked      = 1u << 3,
  SF_Conflicted     = 1u << 4,
  SF_Ahead          = 1u << 5,
  SF_Behind         = 1u << 6,
  SF_StashPresent   = 1u << 7,
  SF_Computing      = 1u << 8,   // Broker 正在计算（菜单显示"计算中"）
};

class SnapshotReader {
public:
  static SnapshotReader& Instance();
  // 从 path（已探测到 repoRoot）取状态；返回 false = 未知
  bool TryGet(const std::wstring& repoRoot, SnapshotSlot* out) noexcept;
private:
  HANDLE m_mapping = nullptr;   // 首次使用后缓存，避免每次 OpenFileMapping
  const uint8_t* m_base = nullptr;
};

} // namespace grt
```

读取算法（**seqlock**，读者永不阻塞写者、无需锁）：

```
loop (最多 3 次重试):
  seq0 = base->seq (acquire)
  if (seq0 & 1) continue              // 写入中
  读取 header(slotCount/ver) 与目标槽
  seq1 = base->seq (acquire)
  if (seq0 == seq1) → 数据一致，采用
否则 → 视为"状态未知"（返回 false），绝不用撕裂数据
```

**哈希一致性**：`pathHash` 必须是**同一套算法**（FNV-1a 64、输入 = 去 `\\?\` 前缀、`\` → `\`、全部小写化的 UTF-16 仓库根路径、无尾部反斜杠）。该函数放在 `gitrt_core_tiny`，DLL 与 Broker 共用同一实现，并有单元测试锁死测试向量（§13.1）。

### 4.8 崩溃防护、生命周期与调试

| 项 | 做法 |
| --- | --- |
| `DllMain` | 只做 `DisableThreadLibraryCalls`；**不创建对象、不做 I/O、不加锁** |
| 引用计数 | `m_ref` 用 `InterlockedIncrement/Decrement`；`DllCanUnloadNow` 返回 `S_FALSE`（常驻更稳，避免卸载时序问题） |
| 异常 | 每个 COM 方法 `GRT_COM_TRY/CATCH`；`GetState` 内**禁止**抛异常路径 |
| 崩溃取证 | DLL 内 `SetUnhandledExceptionFilter` 写一条崩溃日志到 `%LOCALAPPDATA%\GitRT\logs\shell-crash.log`（仅写文件，不弹窗），然后 `EXCEPTION_CONTINUE_SEARCH` |
| 加载位置观测 | **⚠️M0-S5**：`app.doctor` 里枚举 `explorer.exe` / `dllhost.exe` 的模块列表，记录 `GitRT.Shell.dll` 出现在哪个进程 → 写入《支持矩阵》 |
| 探针日志 | 编译宏 `GRT_SHELL_PROBE`：把每次 `GetTitle/GetState/EnumSubCommands` 的入参摘要（item 数、selMask、耗时 μs、仓库根）追加到 `shell-probe.log`；**只在开发构建启用** |
| 计时 | `QueryPerformanceCounter` 包住每个方法；超预算（§7.1）写 WARN，便于在真实机器上收集分布 |

## 5. 共享内存快照与 IPC 协议（wire format）

### 5.1 两条通道的分工

| 通道 | 用途 | 特性要求 |
| --- | --- | --- |
| **共享内存快照**（`Local\GitRT.Status.v1`） | 菜单构建期读状态 | **不阻塞、无系统调用放大**：`OpenFileMappingW` 一次（句柄缓存）+ 内存读 + seqlock 校验 |
| **命名管道**（`\\.\pipe\GitRT.<sid>.v1`） | `Invoke` 转发、长任务流式回传、参数/列表查询 | 请求-响应 + 服务端推送；支持超时与取消 |

**为什么状态不走管道**：管道 `CreateFile` + `ReadFile` 在菜单 UI 线程上是不确定的（可能几十 μs 到几十 ms），而共享内存读是纳秒级。状态查询是**每项每次**都会发生的热路径。

### 5.2 快照内存布局（精确偏移）

```cpp
// 共享内存段 = GrtSnapshotHeader + 256 × SnapshotSlot + 字符串池 + 仓库列表池
#pragma pack(push, 8)
struct GrtSnapshotHeader {              // 偏移 0，大小 64 字节
  uint32_t magic;        // 0x47525453 ('GRTS')  偏移 0
  uint16_t version;      // =1                   偏移 4
  uint16_t headerSize;   // 64                   偏移 6
  volatile uint32_t seq; // ★ seqlock：奇数=写入中 偏移 8
  uint32_t slotCount;    // 256                  偏移 12
  uint32_t slotMask;     // 255（要求 2^n-1）     偏移 16
  uint32_t flags;        // 1 = Broker 正在全量校准 偏移 20
  uint64_t publishedMs;  // Broker 启动时刻（GetTickCount64） 偏移 24
  uint32_t pathPoolOffset;  // 从段首算起          偏移 32
  uint32_t pathPoolSize;
  uint32_t repoListOffset;  // 已知仓库根路径列表（doctor/仪表盘用）
  uint32_t repoListCount;
  uint8_t  reserved[16]; // 偏移 48..64
};
static_assert(sizeof(GrtSnapshotHeader) == 64);
static_assert(offsetof(GrtSnapshotHeader, seq) == 8);
#pragma pack(pop)
```

- **槽位表**：256 个 `SnapshotSlot`（§4.7，32 字节/槽 = 8KB），开放寻址（线性探测，最多 8 次）。
- **字符串池**：UTF-16、`\0` 结尾、4 字节对齐；仅用于诊断显示（如"哪个仓库"），菜单热路径不读。
- **段总大小**：64 + 8KB + 32KB(pool) + 64KB(repoList) ≈ 108KB，固定大小，一次 `CreateFileMappingW` 建立。

**写入协议（Broker 侧，`snapshot_writer`）**

```
BeginWrite():  InterlockedIncrement(&hdr->seq);   // → 奇数
  ... 原地更新槽位/池 ...
EndWrite():    InterlockedIncrement(&hdr->seq);   // → 偶数
```
写者只在**内存中**改动，不调用任何阻塞 API；整个写入通常 < 50 μs，读者重试 3 次几乎必然成功。

**版本兼容**：`version` 不匹配 → DLL 视为"快照不可用"（菜单退化），并记一条日志。**绝不假设布局相同**。

### 5.3 管道帧格式

```
每帧 = 16 字节帧头 + payload（小端，UTF-8 文本或二进制）

struct GrtFrameHeader {          // 偏移
  uint32_t magic;                // 0x47524631 ('GRF1')   0
  uint16_t protoVer;             // =1                    4
  uint16_t type;                 // 见下表                 6
  uint32_t reqId;                // 请求关联               8
  uint32_t payloadLen;           // 12
};                               // 共 16 字节
```

| type | 名称 | 方向 | payload |
| --- | --- | --- | --- |
| 0x0000 | `ERROR` | S→C | `{code:int32, message:string}` |
| 0x0001 | `HELLO` | C→S | `{protoVer, clientPid, clientVer, shellVer}` |
| 0x0002 | `HELLO_ACK` | S→C | `{protoVer, brokerVer, capabilities:u32 位集}` |
| 0x0010 | `QUERY_STATE` | C→S | `{repoRoot:string, force:bool}` |
| 0x0011 | `STATE` | S→C | 32 字节 `SnapshotSlot` 原始拷贝 |
| 0x0020 | `INVOKE` | C→S | `{sectionName:string}`（载荷在共享内存段里） |
| 0x0021 | `INVOKE_ACK` | S→C | `{taskId:u32}` |
| 0x0030 | `RUN` | C→S | `{cmdKey:string, cwd:string, pathsSize, paths[], flagsJson:string}` |
| 0x0031 | `PROGRESS` | S→C | `{phase:string, percent:int32, cur:u64, total:u64, text:string}` |
| 0x0032 | `LOG` | S→C | `{level:u8, line:string}` |
| 0x0033 | `ASK` | S→C | `{askKind:u8, prompt:string, choices[]}`（如冲突处理询问） |
| 0x0034 | `ASK_REPLY` | C→S | `{askId:u32, choiceIdx:int32, text:string}` |
| 0x0035 | `DONE` | S→C | `{exitCode:int32, gitArgv:string, elapsedMs:u64, errorCode:u32}` |
| 0x0040 | `CANCEL` | C→S | `{taskId:u32, force:bool}` |
| 0x0050 | `LIST` | C→S | `{kind:u8}`（分支/标签/远端/储藏条目） |
| 0x0051 | `LIST_RESULT` | S→C | `{items:[{value,label,isCurrent,upstream}], truncated:bool}` |
| 0x0060 | `PING` / 0x0061 `PONG` | 双向 | 空 |
| 0x00FF | `BYE` | S→C | `{reason:string}` |

**请求-响应与流式**：`DONE` 前的所有 `PROGRESS/LOG/ASK` 都携带同一 `reqId`；客户端必须容忍乱序，并按 `reqId` 分派。

**管道服务端并发**：每个客户端连接一个线程（`PIPE_UNLIMITED_INSTANCES`），用**重叠 I/O + 事件**实现可取消的读写。

**超时与降级矩阵**

| 调用方 | 操作 | 超时 | 超时后 |
| --- | --- | --- | --- |
| Shell.dll | 菜单期**不做**管道调用 | — | — |
| Shell.dll | `Invoke` 写管道 | 50 ms | 关闭连接 → 直接 `CreateProcess` 启动 Broker（带 `--request-section`） |
| Broker | `HELLO` 握手 | 2 s | 关闭连接 |
| GUI | `QUERY_STATE`（参数面板要分支列表） | 3 s | 显示错误 + "重试" |
| GUI | 长任务 | 无上限（有心跳 `PING` 每 5 s） | 心跳丢失 3 次 → 标记任务"状态未知"并提示查看日志 |

**背压**：`LOG` 在客户端不读时服务端缓冲上限 1 MB；超出丢弃并置 `LOG{dropped:N}`，**绝不**因日志把管道写满而卡住 git 进程。

### 5.4 共享内存请求段（`Invoke` 载荷）

```
名称：Local\GitRT.Req.<GUID>
布局：
  [GrtReqHeader 32B]
     magic 'GRRQ' | ver=1 | size | cmdId:u16 | selMask:u16 | flagsVersion:u32
     callerPid | callerTid | createdMs:u64
  [路径区]  u32 count + count × (u32 byteLen + UTF-16 字节)
  [配置区]  flags 覆盖（JSON，UTF-8，可为空）
```
DLL 写完即 `CloseHandle`（段仍存活，因 Broker 会打开）；Broker 打开、读走、`CloseHandle` → 段自动销毁。段名按时间戳生成，避免并发冲突；Broker 启动时扫描前缀补收遗漏请求（§4.5 兜底）。

## 6. GitRT.Broker.exe 实现

### 6.1 线程模型

| 线程 | 数量 | 职责 | 阻塞点 |
| --- | --- | --- | --- |
| Main | 1 | 隐藏窗口消息泵（接收 GUI IPC、托盘、关机通知 `WM_QUERYENDSESSION`）、启动/退出编排 | `GetMessage` |
| PipeAcceptor | 1 | `ConnectNamedPipe` 循环，接受客户端后交给会话线程 | `ConnectNamedPipe`（overlapped + 事件，可退出） |
| ClientSession | 每连接 1 | 读帧、分派、写 `PROGRESS/LOG/DONE`、心跳 | 管道 I/O（overlapped） |
| StateWorker | 默认 4（1–8 可配） | 执行 `git status` 状态计算 | 等队列 / 等 git |
| TaskRunner | 每长任务 1（并发上限 2） | 执行 pull/push/clone 等并流式回传 | 等 git |
| Watcher | 1（统一管理多个句柄） | `ReadDirectoryChangesW` / `FindFirstChangeNotification` + 去抖 | `WaitForMultipleObjects(64)` |

**线程基础设施**：`std::thread` + `std::mutex` + `std::condition_variable`（MinGW 下由静态 `libwinpthread` 支持，见 §2.4）。**不用** COM STA 线程（Broker 不实现 COM 服务器）。

**两级并发限制（关键）**

```
GlobalGitSemaphore(max=4)：全进程同时运行的 git 进程数上限
PerRepoLock(hash)：同一仓库同时只有一个状态计算/写操作
```

写操作（pull/commit/…）优先于状态计算；写操作运行时**暂停**该仓库的状态计算（避免 `index.lock` 竞争与读到中间态）。

### 6.2 状态引擎

```cpp
// src/broker/state_engine.h
namespace grt {

enum class ComputeReason : uint8_t { MenuOpened, WatcherEvent, TtlExpired, ManualRefresh, Startup };
enum class Priority : uint8_t { High = 0, Normal = 1, Low = 2 };   // 数值小 = 先执行

struct ComputeRequest {
  std::wstring repoRoot;
  uint64_t     hash = 0;
  ComputeReason reason;
  Priority     priority;
  uint64_t     enqueuedMs;
};

class StateEngine {
public:
  void Request(ComputeRequest req);          // 幂等：同 hash 若在队列/运行中则仅标记"需重算"
  void Invalidate(uint64_t hash, bool immediate);
  void OnWriteTaskBegin(uint64_t hash);      // 暂停该仓库状态计算
  void OnWriteTaskEnd(uint64_t hash, bool changed);
private:
  void WorkerLoop();                          // 4 个
};
}
```

**算法要点**

| 规则 | 值/说明 |
| --- | --- |
| 队列 | 按 `Priority` 的三级队列 + FIFO；`MenuOpened` 一律 High |
| 单飞（single-flight） | 每 hash 只允许一个进行中计算；期间新请求置 `dirty` 标志，完成后再跑一次 |
| 去抖 | 同一 hash 在 250 ms 内的重复 `WatcherEvent` 合并 |
| TTL | 默认 3 s（配置 `state.ttlMs`）；菜单打开时若 TTL 过期 → 异步重算，**菜单仍用旧值** |
| 后台校准 | 已知仓库每 30 s（Low 优先级）复查一次，仅在空闲时执行 |
| 失败退避 | 1 s → 5 s → 30 s → 标记未知（`SF_Known` 清除），并写日志 |
| 超时 | 单次 `git status` 超过 10 s（大仓库/慢盘）→ 放弃本次但发布 `SF_Computing`，避免菜单显示过期为"干净" |
| 网络路径 | `RF_Network` → **不计算**（除非配置 `state.allowNetwork=true`） |
| 发布 | 计算完成即 `SnapshotWriter::Publish(hash, slot)`（一次 seqlock 写入） |

**`git status` 调用形态**（唯一形态，见 §7）

```
argv = [git, --no-optional-locks, -c, core.quotepath=false, status,
        --porcelain=v2, -z, --branch, --show-stash, --untracked-files=normal]
env  += GIT_OPTIONAL_LOCKS=0
```

从输出抽取并压缩为快照槽：`SF_Dirty`（任一 `1`/`2`/`u` 条目且 Y≠'.' 或工作区变更）、`SF_Staged`（X≠'.'）、`SF_Untracked`（`?`）、`SF_Conflicted`（`u`）、`SF_Ahead/Behind`（`# branch.ab +N -M`）、`SF_StashPresent`（`# stash N`，N>0）。

### 6.3 目录监视（性能与正确性的折中，需明确写入文档）

**问题**：要 100% 准确地知道"工作区是否变脏"，必须递归监视所有目录（不可接受，大仓库几十万目录），或者依赖 `core.fsmonitor`。

**实现策略（四层，逐层降级）**

| 层 | 监视对象 | 目的 | 成本 |
| --- | --- | --- | --- |
| L1 | `gitDir` 非递归（`index`、`HEAD`、`refs`、`index.lock`、`MERGE_HEAD` 等） | 捕获"暂存/提交/切分支/操作开始结束" | 1 句柄 |
| L2 | 仓库根**非递归** | 捕获根目录下的新建/删除/改名（常见操作） | 1 句柄 |
| L3 | **用户当前正在浏览的目录递归**（由 GUI/菜单上下文提供，深度 ≤ 4、目录数 ≤ 2000） | 覆盖"深处文件被编辑"的场景 | 1 句柄 + 内存 |
| L4 | TTL + 后台校准（§6.2） | 兜底 NET 共享、编辑器写入未触发通知、L2/L3 未覆盖的深层改动 | 0 |

**API 选择**

```cpp
// 单路径、非递归、只需"有变化"信号 → FindFirstChangeNotificationW（最省）
//   用于 L1、L2
// 目录树、需要知道改了哪个文件（用于界面刷新） → ReadDirectoryChangesW（overlapped，16KB 缓冲）
//   用于 L3
```

**参数与行为**

| 参数 | 值 |
| --- | --- |
| `FILE_NOTIFY_CHANGE_*` | `LAST_WRITE \| FILE_NAME \| DIR_NAME \| SIZE`（不用 `SECURITY`/`ATTRIBUTES`，减少噪声） |
| 缓冲 | `ReadDirectoryChangesW` 16 KB，`bWatchSubtree=TRUE`（仅 L3） |
| 去抖 | 收到通知后 300 ms 静默窗口再触发重算 |
| 句柄预算 | 最多 64 个 L1/L2（LRU 淘汰）；L3 最多 8 个并发 RecursiveWatch |
| 失活处理 | `ERROR_NOTIFY_ENUM_DIR`（缓冲溢出）→ 立即全量重算，不尝试解析 |
| 退出 | 所有等待都是 `WaitForMultipleObjects([..., m_stopEvent], ...)`，保证 < 100 ms 退出 |

> **必须在《支持矩阵》中写明**："状态可能滞后于真实工作区，滞后窗口默认 ≤ 3 s；本产品不注册图标覆盖，因此不存在'图标不刷新'的感知问题；菜单/状态面板显示的状态为'最近一次计算结果 + 时间戳'。"

### 6.4 任务执行与流式回传（`task_runner`）

```
TaskRunner::Run(CommandSpec, BuildInput):
  1. precheck()（§7.9）→ 失败：向 GUI 发 ASK 或直接 DONE{errorCode}
  2. BuildCommand()（§7.5）→ argv/cwd/env
  3. OnWriteTaskBegin(hash)   // 暂停状态计算
  4. runner.RunStream(invocation, sink)：
       sink.OnProgress(phase, cur, total) → 写 PROGRESS 帧
       sink.OnLogLine(line)              → 写 LOG 帧（按 §7.8 归类）
       sink.OnAsk(prompt, choices)       → 写 ASK 帧并等待 ASK_REPLY（带超时 5 分钟）
  5. 结束后：OnWriteTaskEnd(hash, changed) → 触发状态重算 + Invalidate 磁盘缓存
  6. 写 DONE{exitCode, gitArgv(脱敏), elapsedMs, errorCode}
```

**取消语义**：`CANCEL{taskId, force}` → `TerminateJobObject`（见 §7.2）。若 git 是 `push`/`fetch`，终止后远端可能已部分完成 → DONE 里带 `partialMayHaveApplied=true`，UI 提示"远端状态可能已改变，建议重新抓取确认"。**取消后如发现 `index.lock` 残留**，提示用户确认删除，不自动删。

### 6.5 生命周期、单实例与权限

| 项 | 设计 |
| --- | --- |
| 启动来源 | ① Shell DLL 的 `Invoke`；② GUI 首次运行；③ 开机自启（配置 `broker.autostart`，**默认关**） |
| 单实例 | `CreateMutexW(Local\GitRT.Broker.v1)`；已存在则把 `--request-section` 请求经管道投递给现有实例后 exit(0) |
| 空闲退出 | 默认**常驻**；配置 `broker.idleExitMinutes`（0=永不退出）。退出后菜单状态退化为"未知"（菜单仍可用） |
| 崩溃恢复 | 无自动重启（避免崩溃循环）；DLL 下次 `Invoke` 时自然拉起；连续 3 次启动失败 → 停止拉起并提示用户跑 doctor |
| 权限 | **永不提权**。若用户以管理员运行 GUI，则使用独立命名后缀 `…-elev`：`Local\GitRT.Broker.v1.elev`、快照段 `Local\GitRT.Status.v1.elev`。**中完整性级别的 Explorer 只读非提权实例的快照**（避免提权进程向低完整性进程暴露数据，也避免管道 ACL 冲突） |
| 会话 | `Local\` 命名空间天然按会话隔离；多用户同时登录互不干扰 |
| 关机 | `WM_QUERYENDSESSION` 时写盘（§8）并 `BYE` 通知客户端 |

### 6.6 Broker ↔ GUI 协作

```
Broker 收到 INVOKE{section}：
  ├─ GUI 已在运行 → 通过 GUI 的管道连接转发（GUI 是 Broker 的客户端，Broker 反向推送）
  └─ 未运行 → CreateProcessW(GitRT.exe, "--request-section <name>")，GUI 启动后连 Broker 取请求
GUI 订阅：连 Broker 后发 HELLO + SUBSCRIBE（复用 QUERY_STATE 之外的订阅帧，v1 用 PING 保活）
```

GUI 单实例由 `Local\GitRT.Gui.v1` 互斥体 + 命名窗口消息（`RegisterWindowMessageW` + `PostMessage`）实现，参数面板只能有一个，多次 `Invoke` 合并为"多标签"。

### 7.2 进程封装（含 Job object 保证不产生孤儿进程）

```
1. CreateJobObjectW(nullptr, nullptr)
   SetInformationJobObject(JobObjectExtendedLimitInformation,
       LimitFlags |= JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_ACTIVE_PROCESS(16))
   ★ 目的：git 会派生 ssh / credential helper / git-lfs / hook 脚本；
          杀掉 git 不杀孙进程会留下孤儿 ssh，占用控制台与网络。

2. 命令行拼接：Win32 引号规则（唯一实现点，有单元测试）：
   - 需要引号：含空格/Tab/换行/引号 或 空串
   - 引号内的反斜杠：紧邻结束引号的连续反斜杠要翻倍
   - 参数一律**不做 shell 解析**（不使用 cmd.exe）

3. STARTUPINFOEXW + PROC_THREAD_ATTRIBUTE_HANDLE_LIST
   ★ 精确控制哪些句柄被子进程继承（只继承 3 个 stdio + job 相关），
     避免把 Broker 的监视句柄/管道句柄泄漏给 git 及其 hook。
   CreateProcessW(..., CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT |
                       EXTENDED_STARTUPINFO_PRESENT | CREATE_SUSPENDED, ...)

4. AssignProcessToJobObject(job, pi.hProcess)
5. ResumeThread(pi.hThread)
6. 等待：WaitForMultipleObjects({hProcess, hCancelEvent}, timeoutMs)
7. 清理：CloseHandle×n、TerminateJobObject（失败路径）、CloseHandle(job)（KILL_ON_JOB_CLOSE 生效）
```

**超时/取消的差异化处理**：`git fetch/push` 这类网络操作默认无超时（用户可能正在等凭据输入），但有心跳 `PING`；`git status` 等只读操作默认 10 s 超时。

### 7.3 环境变量矩阵

**先做减法（从父进程环境继承中删除）**——防止宿主环境泄漏导致诡异行为：

```
GIT_DIR  GIT_WORK_TREE  GIT_INDEX_FILE  GIT_OBJECT_DIRECTORY  GIT_COMMON_DIR
GIT_NAMESPACE  GIT_PREFIX  GIT_ALTERNATE_OBJECT_DIRECTORIES
GIT_CONFIG_PARAMETERS   ← 可能被 hook/脚本注入，删除并记日志
GIT_TRACE  GIT_TRACE2  GIT_TRACE_PACKET  GIT_TRACE_PERFORMANCE  (除非用户开启诊断)
```

**再做加法（显式注入）**

| 变量 | 值 | 必要性 | 理由 |
| --- | --- | --- | --- |
| `GIT_TERMINAL_PROMPT` | `0` | **必需** | 无终端时子进程可能永久阻塞等待输入 |
| `GIT_PAGER` / `PAGER` | `cat` | 必需 | 防止 `less` 挂起 |
| `LC_ALL` / `LANG` | `C` | **必需** | 强制英文输出，才能用稳定的模式匹配做错误映射（§7.8）；中文由 UI 层翻译 |
| `GIT_ASKPASS` `SSH_ASKPASS` | `GitRT.AskPass.exe` 绝对路径 | 视配置 | 见 §10；若检测到 GCM 已配置则不注入 |
| `SSH_ASKPASS_REQUIRE` | `force` | 可选 | OpenSSH ≥ 8.4 才生效，特性探测 |
| `GIT_CEILING_DIRECTORIES` | 盘符根 + 用户配置 | 可选 | 阻止向上遍历到慢的网络/家目录 |
| `GIT_OPTIONAL_LOCKS` | `0` | 状态查询时 | 只读查询不写 index（等价 `--no-optional-locks`） |
| `GIT_ADVICE` | `0` | 可选 | 抑制建议输出（git ≥ 2.45 才识别，旧版本忽略无副作用） |
| `GIT_REDIRECT_STDIN/STDOUT/STDERR` | 命名管道名 | ⚠️M0 | Git for Windows 的重定向能力；**未实测通过前用匿名管道 + HANDLE_LIST**（§7.4） |
| `GIT_LFS_SKIP_SMUDGE` | **不设置** | — | 尊重用户 LFS 配置 |

**明确不覆盖**：`core.autocrlf` `core.symlinks` `core.fileMode` `http.proxy` `credential.*` `user.*` `commit.gpgsign` `pull.rebase`——这些是用户的仓库语义，**任何覆盖都会造成"CLI 和我预期不一致"的 bug**。唯一例外：状态查询时注入 `-c core.quotepath=false`（不影响语义，只影响输出编码）。若某命令确实需要临时覆盖（例如 `-c core.editor=`），只在 argv 层用 `-c` 且必须在参数面板预览中可见。

### 7.4 stdio 通道

```
主方案（不依赖 git 特性）：
  CreatePipe ×3（in/out/err）→ SetHandleInformation(读端/写端按需 not-inheritable)
  → STARTUPINFO 标准句柄 + PROC_THREAD_ATTRIBUTE_HANDLE_LIST 精确继承
  → 读端用 overlapped I/O，在【两个独立线程】上同时读 stdout 与 stderr
     ★ 必须同时读：只读一个管道会在另一个填满（默认 64KB）时把 git 卡死 —— 这是 GUI 调 CLI 最经典的死锁
备选方案（⚠️M0 实测后启用）：
  GIT_REDIRECT_STDOUT=\\.\pipe\GitRT.Out.<id> 等；优点是可多读者、可断开重连
```

**解码**：

| 输出类型 | 处理 |
| --- | --- |
| 普通文本（stderr、log、progress） | 按 UTF-8 解码；非法字节用 `U+FFFD` 替换并继续（**绝不因解码失败中止操作**） |
| `status --porcelain=v2 -z` | **不做行分割**，直接按 NUL 切分（路径可能含 `\n`） |
| 路径 | 保持 UTF-8 字节原样以备后续用 `-z` 比对；仅在显示时转 UTF-16 |
| 大输出保护 | 单次调用捕获上限 32 MB（超出截断 + 记录 `truncated=true`）；日志流式回传不占内存 |

**行/块切分**：读线程把 chunk 交给 `LineSplitter`（处理 `\r\n`、`\r`（进度）、`\n`），进度行额外走 §7.7 解析器。

### 7.6 `--porcelain=v2 -z` 解析器

```cpp
// src/core/porcelain_v2.h
namespace grt {

struct StatusEntry {
  char         x = '.', y = '.';   // X=暂存侧, Y=工作区侧
  uint32_t     sub = 0;            // 子模块状态字段
  std::string  path;               // 原始字节（UTF-8，未转义）
  std::string  origPath;           // 仅 type 2（重命名/复制）
  char         type = '1';         // '1' | '2' | 'u' | '?' | '!'
};

struct RepoStatus {
  std::string  headOid, headName;  // # branch.oid / # branch.head
  std::string  upstream;           // # branch.upstream
  int32_t      ahead = 0, behind = 0;   // # branch.ab +N -M
  int32_t      stashCount = 0;     // # stash N
  bool         detached = false;   // head = "(detached)"
  std::vector<StatusEntry> entries;
  bool         truncated = false;
};

RepoStatus ParsePorcelainV2(std::string_view bytes);   // 输入为含 NUL 的原始输出
}
```

**解析规则（容易踩错，逐条实现 + 测试向量）**

| 输入形态 | 处理 |
| --- | --- |
| 以 `#` 开头 | header 行：**在 `-z` 模式下 header 同样以 `NUL` 结尾**（不是 LF！）→ 解析器可以**统一按 NUL 切分**，无需为 header 特判换行 |

> **实测证据（本机 git 2.53.0.windows.3，2026-09-24 用 `cmd /c "... > out.bin"` 抓原始字节）**
>
> ```
> # branch.oid 6c477e5c…c8 <NUL> # branch.head main <NUL> # stash 1 <NUL> ? o.bin <NUL> ? renamed.txt <NUL>
> ```
>
> 同时确认三条"header 是可选的"：
> ① 空仓库时 `# branch.oid` 的值为字面量 `(initial)`；
> ② **没有配置 upstream 时完全不出现 `# branch.ab +N -M`**；
> ③ `# stash N` 只在 `N > 0`（确有储藏）时出现。
> → 解析器必须把"header 缺失"当作正常情况（默认 `ahead=behind=stashCount=0`），**绝不能因为缺少某行而判定解析失败**。
| `1 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <path>` | 普通变更条目，以 NUL 结尾 |
| `2 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <X><score> <path>` | **重命名/复制**：`-z` 模式下 `path` 之后**紧跟一个额外的 NUL 分隔的 `origPath`** → 解析器必须多消费一个 token |

> **实测证据（同一次抓取）**：`git mv a.txt b.txt` 后
>
> ```
> 2 R. N... 100644 100644 100644 c1b0730e… c1b0730e… R100 b.txt <NUL> a.txt <NUL> ? r.bin <NUL>
> ```
>
> 即 `… R100 b.txt\0a.txt\0`：**新路径在前、旧路径在后**，两者各自以 NUL 结尾。
> 作为对照，**不加 `-z`** 时同一条目是 `… R100 b.txt\ta.txt\n`（**用 TAB 分隔**）——这正是我们必须始终使用 `-z` 的原因：TAB/LF 都可能是合法文件名字符，而 NUL 不可能。
| `u <XY> <sub> <m1> <m2> <m3> <mW> <h1> <h2> <h3> <path>` | 未合并（冲突）→ 置 `SF_Conflicted` |
| `? <path>` | 未跟踪 |
| `! <path>` | 被忽略（仅在 `--ignored` 时出现，我们不请求） |
| 空 token | 跳过（`-z` 会产生尾随 NUL） |

**路径编码**：`-c core.quotepath=false` 后路径为原始 UTF-8（不再有 `\303\251` 这类八进制转义）。**仅在显示**时转 UTF-16。

`fetch/push/clone/checkout/submodule/lfs` 必须显式加 `--progress`（stderr 非 tty 时 git 默认关闭进度）。

## 8. 状态缓存与磁盘格式

### 8.1 三级缓存

| 级 | 位置 | 内容 | 生命周期 |
| --- | --- | --- | --- |
| L1 | Shell DLL 进程内 | `ProbeRepo` 结果 LRU(64)、快照段句柄、`LoadString` 串缓存 | Explorer 生命周期 |
| L2 | Broker 内存 | `hash → RepoState{flags, ahead, behind, stash, lastMs, lastErr, watcher}` | Broker 生命周期 |
| L3 | 磁盘 `%LOCALAPPDATA%\GitRT\cache\state.v1.bin` | 状态 + 校验字段 | 跨启动（冷启动可用） |

### 8.2 磁盘格式（`state.v1.bin`）

```
[Header 32B]
  magic      u32  'GRTC' (0x43545247)
  version    u16  = 1
  headerSize u16  = 32
  entryCount u32
  poolOffset u32          // UTF-16 路径池偏移
  poolSize   u32
  reserved   u32
  crc32      u32          // 覆盖整个文件（除本字段）

[Entry 48B] × entryCount      // 按 pathHash 升序，便于二分
  pathHash     u64
  rootLen      u16          // 池内字符数
  rootOffset   u32
  flags        u32          // RepoFlag | StatusFlag
  ahead        i32
  behind       i32
  indexMtime   u64          // 校验：gitDir\index 的 mtime (FILETIME)
  indexSize    u64
  headMtime    u64          // 校验：gitDir\HEAD 的 mtime
  computedMs   u64          // 计算时刻（Unix ms）
  reserved     u32

[Pool]  UTF-16LE 路径池（4 字节对齐）
```

**读校验**：逐条比较 `indexMtime/indexSize/headMtime` 与当前文件属性；不一致 → 丢弃该条（**不丢整文件**）。`crc32` 不匹配 → 整个文件作废。

**写策略**：状态变化累积 ≥ 32 条 或 距上次落盘 ≥ 30 s 或 收到关机通知 → 原子写（写 `state.v1.tmp` → `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`）。写入失败只记日志，**不得影响功能**。

### 8.3 冷启动路径（用户体验关键）

```
Broker 启动
 ├─ 读 state.v1.bin → 立即 Publish(L2→快照，带 SF_Known，但 updatedMs 为历史时刻)
 ├─ 打开管道、开始接受客户端
 ├─ 异步排队：所有已知仓库的 Low 优先级重算
 └─ 结果：菜单第一次右键就有状态可显示（tooltip 标注"上次于 HH:mm"），不会显示"未知"
```

### 9.4 差异查看器（`diff_view`）

| 项 | 规则 |
| --- | --- |
| 数据源 | `git diff --no-color [--staged] -- <paths>`；二进制用 `git diff --numstat` 判定（`-\t-`） |

### 9.5 进度窗口（`progress_window`）

> ★ **实现修订（2026-09-24，按产品负责人要求"点击执行应出现对应命令行反应并刷新状态"）**：
> 下表"显示延迟/成功即静默关闭"两行**已废弃**。现在的行为：
> ① **点执行立即出现**（不再等 1500 ms）——用户必须马上看到"正在跑什么命令"；
> ② 窗口标题与日志第一行都是**真实命令行**（`命令名 — git <完整 argv>`、`> git …`）；
> ③ 结束**一律保留窗口**（成功/失败/取消都一样），显示 `--- 已完成 (N ms)` 或 `--- 失败 (exit=N)`，
>    Close 或 **Esc** 关闭；运行中禁止关闭（防误关正在跑的命令）；
> ④ 结束**一律刷新状态**：向主窗口发 `WM_GRT_STATUS_RELOAD(wp=1)` → **重新读 `git status`** →
>    刷新状态面板与底部状态栏。旧实现只在"静默成功的短命令"这一条路上发通知，慢命令与失败路径都不刷新，
>    这正是"执行完状态没变"的根因。

| 行为 | 值 |
| --- | --- |
| 显示时机 | **点执行立即显示**（`WM_CREATE` 里 `SW_SHOW`；早期实现的 1.5 s 延迟已移除） |
| 标题 | `命令名   —   git <完整命令行>`（窗口标题带命令名，便于任务栏区分） |
| 日志区 | 流式输出，**第一行就是真实命令行**（`> git …`，逐条命令各一行） |
| 阶段显示 | 本地化阶段文本 + 百分比（从 `Receiving objects: 43%` 之类行里提取） |
| 取消 | 按钮 → `CANCEL` → 按钮变"取消中…"直到 `DONE` |
| 结束 | **保持打开**（成功/失败/取消一致）并显示耗时或退出码；Close / Esc 关闭 |
| 状态刷新 | 结束后 `WM_GRT_STATUS_RELOAD(wp=1)` → 重读 `git status` → 状态面板 + 底部状态栏 同步 |

### 9.5d 合并提交（squash，复选连续提交）

| 项 | 说明 |
| --- | --- |
| 入口 | 命令表 `commit.squash`（1108，`ExecKind::Internal`，`Danger::Destructive`）→ 命令列表/AI 之外的菜单项都能进；窗口 `src/gui/squash_window.cpp`（类 `GitRT.SquashWindow`） |
| 界面 | 带复选框的提交列表（`LVS_EX_CHECKBOXES`，沿第一父链，最新在最上）+ **合并后的提交信息（可编辑，勾选变化自动预填）** + 执行日志（真实命令行 + 输出）+ 合并/刷新/关闭 |
| 即时反馈 | `WM_NOTIFY`/`LVN_ITEMCHANGED` 检测"勾选状态位"变化 → 刷新状态行（`已选 N 条：连续 ✓ / 不连续 ✗ / 含合并提交 ✗`）、预填信息、启用/禁用按钮 |
| 核心 | `src/core/squash.{h,cpp}`：`LoadCommitList`（`git log --first-parent`，`%H%x1f%h%x1f%an%x1f%ad%x1f%P%x1f%s`）、`BuildSquashPlan`、`ApplySquash`。**UI 只做提示，判定与拒绝理由全部来自 core** |
| 两条执行路径 | ① 区间触到 HEAD：`git reset --soft <最旧选中的父>` + `git commit -m <合并信息>`（索引不变 ⇒ 新 tree = 合并后的改动）；② 不含 HEAD：`git commit-tree <最新选中的 tree> -p <最旧父> -m <信息>` + `git rebase --onto <新提交> <最新选中>`（新 tree 与原最新选中的 tree 相同 ⇒ 重放**不会冲突**） |
| 语义 | 改动 = 所有选中提交的改动之和（= 最新选中的 tree）；提交信息 = 各 subject 从旧到新按行拼接（可手改） |
| 拒绝条件（都在 core，UI 直接展示） | 少于 2 条 / 非十六进制 / 不在第一父链上 / **不连续** / 含 merge / 触到根提交 / 区间之上有 merge / 暂存区脏（`diff-index --cached`）/ 有未完成的 rebase·merge·cherry-pick |
| 确认 | 执行前 `MessageBox(MB_YESNO\|MB_DEFBUTTON2\|MB_ICONWARNING)`：列出条数、合并后的信息、模式与将执行的命令 |
| 执行 | 工作线程跑 `ApplySquash`，逐条把 `> git …` 与输出回投到窗口日志（`WM_GRT_TASK_LOG`）；完成后刷新列表并 `WM_GRT_STATUS_RELOAD(wp=1)` 让主窗口重读 `git status` |
| 日志保留 | 合并完成后**不清日志**（要能回看真实命令行）；只有「刷新」或开始新一次合并才清 |
| CLI/脚本 | `GitRT.exe --squash <h1,h2,h3> [--message <文本>] [--cwd <repo>] [--dry-run] [--out <file>]`（与 GUI 同一套 core） |
#### 9.5e 克隆选项（深度等）

| 选项 | argv | 类型 | 说明 |
| --- | --- | --- | --- |
| 深度 | `--depth=<n>` | 值型 | 浅克隆；**留空 = 完整克隆**。必须是正整数，构造期就拦（见下） |
| 单分支 | `--single-branch` | 开关 | 只拉一个分支（常与深度同用） |
| 分支 | `--branch=<b>` | 值型 | 指定分支/标签（`IsValidBranchName` 校验） |
| 不拉标签 | `--no-tags` | 开关 | 不跟随标签 |
| 部分克隆 | `--filter=<spec>` | 值型 | 如 `blob:none`；只允许字母数字与 `: , = + - . /` |
| 递归子模块 | `--recurse-submodules` | 开关 | 原有的选项 |

- 新增 `ValidateFlagValues()`（`command_builder.cpp`）：值型 flag 的白名单式校验。`--depth=abc` 这类输入在**构造期**就被拦下并给出中文原因，而不是等 git 报一句难懂的错（回归：GUI 自检 + `tools\test-clone.ps1` 用例 ②）。
- **克隆的落地目录**：`repo.clone` 是"不需要仓库"的命令，它的工作目录取**用户选中的那个目录**（GUI）/`--cwd` 的字面值（CLI）。这条规则见偏差 24。
#### 9.5f 参数面板：查看类自动显示 + 执行输出就地显示

- **内容同源**：查看类命令（`inspect.log` 1401 / `inspect.diff` 1402 / `inspect.filelog` 1403）的文本只在 `BuildViewText()` 里产生一次；点「执行」用 `ShowTextWindow` 打开完整窗口，面板则调同一个函数把内容显示在自己的预览框里（标题改为「内容（自动刷新）」）。
- **自动刷新**：面板对查看类命令挂 `kTimerPreview`（2.5s），到点且窗口可见时在工作线程重新拉取，算完 `PostMessage(WM_GRT_PANEL_PREVIEW)` 回投（`previewBusy` 防重入）。`git` 调用**绝不在 UI 线程**。
- **就地执行**：`progress_window.cpp` 把执行主体抽成 `RunCommandSequence(hwnd, spec, cmd, cancel, oc)`，进度窗口（`WorkerProc`）与新的 `RunBuiltCommandOn(target, …)` 共用它。参数面板的「执行」走 `RunBuiltCommandOn`：日志/进度/结束消息都投给面板自己（`WM_GRT_TASK_LOG` / `PROGRESS` / `DONE`），于是输出直接落在面板的「运行结果」框里，**不再另开窗口**。
  - 结束仍然发 `WM_GRT_TASK_FINISHED` 给宿主窗口（AI 助手窗口靠它显示"运行结果"）、并发 `WM_GRT_STATUS_RELOAD(wp=1)` 给主窗口，保持"执行完必刷新"的既有保证。
  - 运行中「执行」按钮变「取消」（同一个按钮，第二次点击 `CancellationToken::Cancel()`）。
- **布局**：面板 `st->stack` 用"负高度 = 弹性"，现在支持多个弹性项（「将执行的命令」与「运行结果」各占一半）。
#### 9.5g AI 规划：可配置系统提示词 + "方案直接输出命令"

- **系统提示词可配置**：`AiConfig.systemPrompt`（存 `GitRT.ai.json` 的 `systemPrompt` 键，界面里就是首选项 →「系统提示词」，可多行、可「恢复默认提示词」）。`EffectiveSystemPrompt(cfg, titleRes)` 决定实际用哪个：填了 → **原样使用**（用户可以完全改写模型行为）；留空 → 内置默认 `BuildPlannerSystemPrompt()`。GUI/CLI 三处调用点统一走它。
- **两条规划路线**（模型二选一，`cmdline` 优先）：
  1. `{"cmdline":"git status -sb", …}` —— **直接给命令**（"方案应该直接输出命令"）。默认提示词里明确：查看类需求（当前分支/状态/历史/差异）优先走这条。
  2. `{"command":"<命令表 key>", "params":{…}, "flags":{…}}` —— 写操作（提交/推送/合并/重置）只能走命令表，避免模型一句话改写仓库。
- **只读白名单**（`ParseReadOnlyGitCommand()`，`PlanToCommand()` 的安全闸门）：
  - 整条只读的子命令：`status log show diff rev-parse rev-list describe shortlog blame for-each-ref ls-files ls-tree cat-file reflog name-rev merge-base count-objects whatchanged grep diff-tree diff-index diff-files version help var`。
  - 需要看参数才算只读的：`branch`（只允许 `-` 开头的参数，"裸名字"= 可能在建分支 → 拒）、`tag`（必须 `-l/--list`）、`remote`（`-v/--verbose/show/get-url`）、`stash`（`list/show`）、`config`（`--get*/--list/-l`）、`worktree`（`list`）、`submodule`（`status/summary`）。
  - 其余（`push/pull/fetch/reset/commit/merge/rebase/clean/rm/stash push…`）一律拒绝 → 提示"写操作请用命令表"。
  - 命令行按 argv 切分（支持引号，**不经 shell**），`git` 作为 exe、其余作为 argv 交给既有的执行通道。
- 界面：方案区对这条路线显示「模型直接给出的只读命令：git …」+「即将执行的命令」；执行走与其它命令相同的通道（参数面板就地显示/AI 窗口）。
#### 9.5h 远端跟踪与按提交还原

**一、远端基线（"所有提交以远端提交为基、往上累加"）** —— `src/core/remote.{h,cpp}`

| 读出什么 | 怎么读 |
| --- | --- |
| 上游 | `git rev-parse --abbrev-ref --symbolic-full-name @{upstream}`（失败 = 没设上游，不是错误） |
| 领先/落后 | `git rev-list --left-right --count <upstream>...HEAD` → `落后\t领先` |
| 本地新增（在远端之上） | `git rev-list HEAD --not <upstream>` |
| 远端新增（本地还没有） | `git rev-list <upstream> --not HEAD` |
| 基线提交列表 | 两段拼起来：上段 `git log --first-parent HEAD --not <upstream>`（本地新增，最新在前），下段 `git log --first-parent <upstream>`（远端基线及以下）；每条标注 `localOnly`/`remoteOnly` |
| 远端分支 | `git for-each-ref --sort=-committerdate refs/remotes`，`origin/HEAD` 标为"远端默认分支"、当前上游标 `[当前上游]` |
| 远端地址 | `git remote` + `git remote get-url [--push] <name>` |

- 「提交历史」（`inspect.log`，1401）的正文改成：**基线说明 + 两段提交列表（【本地】/【远端新增】/【远端】）+ 原提交图**。因为面板对查看类命令有 2.5 秒自动刷新，抓取完不用手点就会更新。
- 状态视图的"领先/落后"格子加上上游名：`origin/main   +2 / -1`；没上游时显示"未设置上游（「远端分支…」里可以设置）"。
- **持续跟踪**：首选项里的「自动抓取间隔（分钟，0=关闭）」（配置键 `autoFetchMinutes`，写进 config.json）。主窗口 `kTimerAutoFetch` 每 60 秒看一眼，到点且不在抓取中就在**工作线程**里 `git fetch --prune`，完成后给主窗口发 `WM_GRT_STATUS_RELOAD(wp=1)` 重读状态；失败只写日志（离线是常态，不弹框打扰）。

**二、远端分支与地址窗口**（`remote.panel`，`src/gui/remote_window.cpp`）

- 远端分支列表（`LoadRemoteBranches`）+ 抓取 / 检出 / 新建跟踪分支 / 设为上游；下半是远端地址：下拉（`LoadRemotes` 的 name）+ 地址框 + 「保存地址」(`SetRemoteUrl`) / 「添加远端」(`AddRemote`)。
- 校验都在 core：`ValidateRemoteName`（字母数字与 `- _ .`，不能以 `-` 开头）、`ValidateRemoteUrl`（非空、不以 `-` 开头、不能有引号/控制字符；**带空格的本地路径算合法**，不误杀）。
- 「检出」复用 `BuildRestorePlan(..., RestoreMode::NewBranch, <本地分支名>)` + `ApplyRestore`，走的是同一套校验与日志通道。

**三、按提交还原**（`history.restore`，`src/core/restore.{h,cpp}` + `src/gui/restore_window.cpp`）

| 模式 | 命令 | 语义 |
| --- | --- | --- |
| 只读检出（默认） | `git checkout --detach <提交>` | 工作区变成该提交的样子，**不动任何分支**，随时切回 |
| 从该提交新建分支 | `git checkout -b <新名> <提交>` | 以它为新起点继续干活 |
| 重置 · 软 | `git reset --soft <提交>` | 后续提交从历史里去掉，改动进**暂存区** |
| 重置 · 混合 | `git reset --mixed <提交>` | 改动留在**工作区**（未暂存） |
| 重置 · 硬 | `git reset --hard <提交>` | 丢弃改动（**未跟踪文件保留**） |

- 拒绝条件（`BuildRestorePlan`）：非十六进制哈希 / 哈希不存在 / 未完成的 rebase·merge·cherry-pick（查 `.git/rebase-merge` 等）/ 新建分支没给名字或名字非法或已存在。
- 提示（不拒绝）：分离头指针说明、工作区脏、`dropCount` 与其中**已推送到远端**的条数（`git rev-list <目标>..HEAD [--not <upstream>]`）→ 会与远端分叉的告警。
- **二次确认**：脏工作区 + 硬重置时 `plan.needsExtraConfirm = true`；界面先弹 `IDS_RST_HARD_TITLE/BODY`，确认后才重建计划（`forceHard=true`）；脚本里等价于必须显式 `--force`，否则 CLI 直接拒绝。
- 命令行展示与执行都走 `plan.commandLines` / `ApplyRestore`，日志逐条打 `> git …` 与输出（与其它窗口一致）。

**四、CLI（脚本/CI 用，与界面同一套 core）**

```
--remote-info [--remote-fetch]        报告上游/领先落后/本地新增/远端分支/远端地址/基线文本
--set-upstream <origin/main>          设置上游
--remote-add name=url                 新增远端
--remote-set-url name=url             改远端地址
--remote-remove <name>                删除远端
--restore <hash> --mode detach|branch|soft|mixed|hard [--branch <名>] [--force] [--dry-run]
```

#### 9.7c 标签与发布（tag.* / release.*）

核心在 `src/core/tag.h|.cpp` 与 `src/core/release.h|.cpp`，沿用 `restore.*` 的**计划/执行**范式：
组装计划时把所有校验做掉并给出中文原因，同时把要跑的 argv 逐条准备好；执行只负责照单跑。

- `TagInfo{name,hash,shortHash,subject,date,annotated,onRemote}` + `LoadTags()`：
  `git for-each-ref refs/tags --format=…`，**分隔符用 `%09`(Tab)**（`for-each-ref` 不支持 `%x1f`，会输出字面量；`remote.cpp` 已踩过），
  subject 里再有 Tab 时把剩余字段拼回去；再用 `git ls-remote --tags <remote>` 标 `onRemote`（失败/离线**不算致命**，全 false 返回 true）。

- `TagPlan{ok,error,name,target,message,annotated,force,forceNeeded,op,destructive,commandLines,argvList,warnings}`

  | 动作 | 构造器 | 命令 | Danger |
  | --- | --- | --- | --- |
  | 新建（轻量） | `BuildTagPlan(…,annotated=false)` | `git tag <n> <rev>` | Careful |
  | 新建（附注） | `BuildTagPlan(…,annotated=true)` | `git tag -a <n> -m <m> <rev>` | Careful |
  | 覆盖 | 同上 + `force=true` | 追加 `-f`（并给 warning） | Careful |
  | 推送 | `BuildPushTagPlan(name\|all,remote)` | `git push <r> <n>` 或 `git push <r> --tags` | Careful |
  | 删除 | `BuildDeleteTagPlan(name,remote,remoteName)` | `git tag -d <n>` / `git push <r> :refs/tags/<n>` | **Destructive** |

  校验：名字先过 `git check-ref-format refs/tags/<n>`；同名已存在且未 force → 拒绝；`target` 空 = `HEAD`，用 `git rev-parse --verify <rev>^{commit}` 校验。
  删除计划里 `destructive=true`，CLI 必须 `--force`、GUI 必须二次确认（默认按钮「否」）。
  `ApplyTagPlan()` 逐条 `RunGitSync`，任一条失败即停，把每步的 `commandLine/exitCode/out/err` 收进 `TagResult`（与 `ApplyRestore` 同形）。
  `DescribeTags()` 给面板用的多行中文文本（标出「附注/轻量」「本地/远端」）。

- `GhInfo DetectGh()`：PATH 上找 `gh.exe`；没有就给中文提示 `winget install GitHub.cli`，**功能禁用而不是崩**。
- `ReleasePlan` + `BuildReleasePlan()`：标签必须已存在（否则拒绝）；可选先 `git push origin <tag>`；
  然后 `gh release create <tag> --title <t> [--notes <n>\|--generate-notes] [--draft] [--prerelease] <assets…>`，
  附件**逐个检查存在性**，缺了就拒绝并指名。`release.create` 是 Careful（会公开），不是 Destructive。
- `LoadReleases()` 用 `gh release list --limit 30 --json …`（极简手写解析，不引新依赖）；gh 不可用 → 空列表 + 中文 error。
- CLI：`--tag-list/--tag-create/--tag-push/--tag-delete/--release-list/--release-create`，输出仍是 `key=value`（`ok=` 结尾），删除要 `--force`。
- 命令表：`tag.list`(2307) / `tag.create`(2308) / `tag.push`(2309) / `tag.delete`(2310) / `release.list`(2311) / `release.create`(2312)。

## 10. GitRT.AskPass.exe 实现

| 项 | 设计 |
| --- | --- |
| 调用契约 | git 以 `GIT_ASKPASS <prompt>` 调用，提示语在 `argv[1]`；答案写 **stdout 第一行 + `\n`**；退出码 0 = 成功 |
| 提示语分类 | `Username for '...'` → 用户名；`Password for '...'` → 密码/令牌；`Passphrase for key '...'` → 私钥口令；其它 → 通用密码框 |
| 凭据复用 | 先查 Windows 凭据管理器（`CredReadW`，target 前缀 `GitRT:`）→ 命中且 URL 匹配则**静默返回**（实现"推送不再输密码"） |

| 未启用 `desktop5:ItemType` 之外的元素 | 保持最小，减少校验失败面 |

### 11.3 `packaging/scripts/build-msix.ps1`（施工图）

```powershell

  [string]$Config  = 'Release',
  [string]$OutDir  = "$PSScriptRoot\..\..\build",
  [switch]$DevCert = $true,
  [string]$CertPfx = "$PSScriptRoot\..\..\build\dev.pfx",

function Find-SdkTool([string]$name) {
  $c = Get-Command $name -ErrorAction SilentlyContinue; if ($c) { return $c.Source }
  $roots = @("${env:ProgramFiles(x86)}\Windows Kits\10\bin", "$env:ProgramFiles\Windows Kits\10\bin")
  $hit = Get-ChildItem $roots -Recurse -Filter $name -ErrorAction SilentlyContinue |
         Where-Object { $_.FullName -match '\\x64\\' } | Select-Object -First 1
  if (-not $hit) { throw "$name 未找到：请安装 Windows SDK（仅打包需要）" }
  return $hit.FullName

$makeappx = Find-SdkTool 'makeappx.exe'; $signtool = Find-SdkTool 'signtool.exe'

# 1) 组装 sparsePack 目录（清单 + 占位图片）

if ($LASTEXITCODE -ne 0) { throw "makeappx 失败 ($LASTEXITCODE)" }

# 3) 签名（开发期自签名；发布期替换为 SignPath / OV 证书）
if ($DevCert -and -not (Test-Path $CertPfx)) {
  $c = New-SelfSignedCertificate -Type Custom -Subject 'CN=GitRT' `
       -KeyUsage DigitalSignature -FriendlyName 'GitRT Dev' `
       -CertStoreLocation 'Cert:\CurrentUser\My' `
       -TextExtension @('2.5.29.37={text}1.3.6.1.5.5.7.3.3','2.5.29.19={text}')

  # 必须把公钥导入 TrustedPeople，否则 Add-AppxPackage 报 0x800B0109
  Export-Certificate -Cert $c -FilePath "$OutDir\dev.cer" | Out-Null
  Import-Certificate -FilePath "$OutDir\dev.cer" -CertStoreLocation 'Cert:\CurrentUser\TrustedPeople' | Out-Null
}
& $signtool sign /fd SHA256 /f $CertPfx /p $CertPwd /tr http://timestamp.digicert.com /td SHA256 $msix
if ($LASTEXITCODE -ne 0) { throw "signtool 失败 ($LASTEXITCODE)" }

# 4) 校验签名
& $signtool verify /pa /v $msix | Out-Host
Write-Host "OK → $msix" -ForegroundColor Green
```

### 11.5 安装器与升级策略

| 场景 | 设计 |
| --- | --- |
| 默认安装（per-user） | `%LOCALAPPDATA%\Programs\GitRT`，**无需 UAC**；身份包 per-user 注册 |
| 全机安装（per-machine） | `%ProgramFiles%\GitRT` + UAC；`Add-AppxPackage -Stage` + `Add-AppxProvisionedPackage -Online` |
| v1 安装器形态 | PowerShell 脚本（`install.ps1` / `uninstall.ps1`），MIT 项目先求可用 |
| v2 安装器 | NSIS（体积小、脚本化）或 WiX；需 Authenticode 签名安装器本身 |

| 卸载残留清单 | 身份包（`Remove-AppxPackage`）、`Installdir`、`HKCU\Software\GitRT`、`%APPDATA%\GitRT`（询问是否保留配置）、`%LOCALAPPDATA%\GitRT`（缓存/日志）、开始菜单快捷方式、托盘注册（`Shell_NotifyIcon` 需显式清理） |

### 11.5b 面向用户的安装/卸载（v0.7 实装）

| 脚本 | 位置 | 做什么 |
| --- | --- | --- |
| `install.ps1` | 发布包根目录（由 `build-release.ps1` 拷贝） | ① 前置检查：Windows 11 22H2+（< 22621 告警）、**开发者模式**（免签名注册必需，未开则给出开启方式并退出）、git 是否在 PATH；② 结束正在运行的 GitRT；③ 铺 `app\*` → `%LOCALAPPDATA%\Programs\GitRT`，`package\*` → 该目录下 `package\`；④ 同版本已注册则跳过，否则（或 `-Force`）先在**独立进程**里 `Remove-AppxPackage` 再 `Add-AppxPackage -Register … -ExternalLocation`；⑤ 跑 `GitRT.ShellProbe.exe --dump` 自检并打印菜单项数；⑥ 重启 explorer。全流程**不需要管理员** |
| `uninstall.ps1` | 同上 | ① 结束进程；② ★ **先备份** `GitRT.ai.json`（明文 Key）到 `%APPDATA%\GitRT\uninstall-backup-<ts>\`（`-RemoveData` 时不备份）；③ 独立进程 `Remove-AppxPackage`（避免 0x80073CFA 半卸载）；④ 删安装目录；⑤ 清理 `HKCU\...\shell\GitRTTest` 传统注册残留；⑥ 可选 `-RemoveData` 删 `%APPDATA%\GitRT` + `%LOCALAPPDATA%\GitRT`；⑦ 重启 explorer。包名解析不依赖源码树：参数 → 安装目录里的清单 → `InstallLocation` 匹配 |

| `install.ps1` 的恢复分支 | — | 若安装目录没有 `GitRT.ai.json` 而 `%APPDATA%\GitRT` 里有 `uninstall-backup-*`，自动恢复最新一份并打印来源（`-NoRestoreBackup` 可关） |

**为什么要有备份**：Key 按产品决策是**明文**存在安装目录里的，卸载删目录就会连 Key 一起删且无法找回。
这条是实机踩出来的教训（见 §16.2 偏差 20），因此"删目录前先备份、装回来自动恢复"是默认行为。

> 开发/测试注意：**不要拿真实安装目录做破坏性卸载演练** —— 用 `-InstallDir <临时目录> -SkipPackage` 或
> `-NoExplorerRestart` 在沙盒目录里验证（本次就是先删了用户真实 Key，才补上备份逻辑）。
